# Classify the supplied workload

1. Read the worksheet and record supplied runtime/OS/architecture, binaries, long-lived processes versus completion jobs, CPU time versus wall time, RAM, concurrency and traffic ranges. Mark each fact supplied, measured or unknown. Never derive resource demand from user count alone.
2. Separate hard constraints from provider preference: required region/data residency, outbound/public IPv4/IPv6, private access, native drivers, storage persistence, RPO/RTO, budget and named operator availability. Ask one batch for only missing facts that change the decision. With no workload, return the worksheet and provisional status; do not recommend a SKU.
3. Consider shared-CPU Cloud Compute for a workload that accepts shared CPU behavior; consider Optimized Cloud Compute when a dedicated CPU ratio is required. Its article separates General Purpose, CPU, Memory and Storage Optimized categories. Treat advertised suitability as a candidate, never a benchmark or capacity promise. [Compute](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/compute.html), [Optimized](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/optimized.html).
4. Consider Bare Metal only for a supplied physical-hardware/isolation need that merits its retained operations. Distinguish physical single-tenant hardware from a dedicated-vCPU VM. Consider Cloud GPU only for a supplied accelerator need; record exact model, GPU count, VRAM, driver/CUDA/ROCm compatibility and region availability as eligibility gates. Product lists do not prove current inventory or performance. [Bare Metal](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/bare-metal.html), [Cloud GPU](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/gpu.html).
5. Treat Managed Databases as a separate data service, not a managed application host. The engine article names MySQL, PostgreSQL, Valkey and Kafka. Confirm the chosen engine's exact version/extensions/privilege/HA/backup constraints from article-body evidence before proposing it. A Marketplace image does not transfer OS/application ownership. [Engines](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/database-engines.html), [Security duties](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/security.html).
6. If Kubernetes is explicitly needed, record VKE control-plane scope while retaining workload security, access, upgrades and monitoring responsibilities. Do not add Kubernetes to solve an ordinary VM fit question. Other managed/serverless products need their own official evidence before qualification. [VKE](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/infrastructure-decision-tools/skills/vultr-platform-stinger/references/research/raw/vke-security.html).
7. Return an eligibility matrix: requirement, candidate product/plan, cited body clause, supplied proof, unresolved gap and status. Supported means documented compatibility only; region stock, actual sizing and runtime behavior stay unproven.
