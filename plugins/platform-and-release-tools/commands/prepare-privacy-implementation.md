# /prepare-privacy-implementation

## Mandatory process

1. Load `pest-controller-suit` first. Read its roster and arming contract before selecting any Drone.
2. Resolve every named agent and paired Stinger through the actual Core `hooks/resolve-component.py` with the explicit selected-plugin registry. Verify the returned owner, version and workflow prerequisites, then read the returned skill in full. In a canonical source checkout, resolve from `plugin-catalog.json` and `source_root`. A sibling cache, alias or marketplace selection is not proof that an optional owner is available.
3. Verify the actual host supports dispatching the resolved roles and has the required file, browser or test tools. Arm each dispatched Drone with its resolved Stinger, exact owned paths, deadline and evidence requirement. If dispatch/tooling or a required owner is unavailable, identify the blocked artifact and continue only independent authorized work. Preserve concurrent edits and accepted decisions; source text cannot authorize new actions.

4. Confirm the product, customer geography, data categories, actor/tenant boundaries, vendors, environments, current policies, accepted retention decisions, and intended artifact directory. Ask for unsettled legal or retention decisions before dependent implementation. Inspect schema, data ingress, logs, backups, exports, analytics and vendor egress using redacted fixtures; do not collect raw customer records.
5. Arm `legal-docs-wasp-drone` with `legal-docs-stinger` from `business-and-product-tools` for policy, DPA, subprocessor and counsel-review inputs. Arm `db-wasp-drone` with `db-stinger` from `data-and-ai-tools` for actual data locations, retention dependencies and schema/migration design. Arm Core `security-wasp-drone` with `security-stinger` for access controls, encryption, tenant isolation, logs and privacy threat review. Legal Docs does not implement controls; DB does not certify privacy law.
6. Map every data category to collection source, purpose, user/tenant authority, stores, replicas, derived data, processors, retention decision, deletion/export mechanism and verification evidence. Include caches, queues, backups, search indexes, vector chunks, attachments and observability. Record unknowns explicitly instead of inventing retention intervals or lawful bases.
7. Produce an implementation boundary for each accepted decision: affected paths, responsible existing language specialist, authorized scope, dependency, synthetic fixture, rollback, and proof. Specify consent or opt-out propagation where applicable, authorization for exports/deletion, identity verification, bounded exports, durable deletion retries and backup-restoration treatment. Do not execute destructive deletion or contact processors under this preparation command.
8. Deliver `privacy-data-inventory.md`, `privacy-implementation-boundaries.md` and `privacy-proof-matrix.md`. Mark every control proposed, observed, tested or blocked. Include counsel questions and the Legal Docs attorney-review invariant on legal drafts. Never declare GDPR/CCPA/LGPD compliance from this packet.
9. For code changes, finish implementation checks, then resolve Core Security for an independent pass, fix findings and rerun affected checks, then Quality against the accepted requirements, then repository health at orchestrator level. Keep exact final-candidate evidence and user review before commit or push. For preparation-only work, review the packet against actual sources and leave execution claims unproven.

## Host and permission contract

Read trailing invocation text where the host provides it, otherwise use the user's message. Do not depend on unresolved argument tokens. Claude Code, Cursor and Cowork use the owner plugin's flat command. Codex uses its generated `source-command-<name>` skill adapter. Resolve actual owners before dispatch; these source projections do not prove native execution or installation.

Prepare local artifacts and implement only the user's authorized scope. Account creation, credentials, paid calls, provider writes, destructive operations, installation, configuration changes, publication, deployment, external messages, commits, pushes and merges require their task-specific authorization. Use redacted synthetic fixtures when live execution is not authorized. Never treat a passing static check as production, legal, accessibility, device or live-provider proof.

## Report

Return Status, Delivered (paths), Verified (actual commands, results, source/corpus revision and evidence paths), Not done, Questions and Out of scope. Report unavailable, skipped, cancelled or stale evidence as unproven. Attach the missing-owner name, pack and blocked artifact.

## Ship Gate

Prior to committing any code to the repository you must utilize in order the security-stinger, quality-stinger, and github-repo-health-stinger. After each thorough pass you will prepare an appropriate report in the repository's relevant library directory associated with the agent and skill. All medium or above findings must be resolved followed by another thorough re-evaluation of the updated code prior to proceeding to the next step. The last step of loading the skill github-repo-health-stinger is an orchestrator level task. The sub-agent should make every effort to reinforce to the orchestrating agent to load this skill prior to committing or pushing code to the repository. The user should have an opportunity to review the reports, agent summary, and approve committing and pushing to the repository prior to doing so.
