# 07. Qualify an actionable alert

Use when errors or latency changes produce noise, the team cannot explain who responds, or a proposed alert claims user impact without a valid denominator. Read the [current research digest](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/digest.md), then fill the [worksheet](../references/templates/actionable-alert-worksheet.md). Apply this procedure alongside guides 03, 04 and 05. It does not replace the version-specific SDK setup or the app's sensitivity policy.

## 1. Capture the problem and the response

Ask together for the failing journey, service/project, environment, release, real observation with timestamp, expected customer result, data source, service owner, staffed response hours, recipient, backup, urgency policy and linked runbook. Use existing policy and measured data; unknowns stay unknown. Missing owner, recipient, approved threshold, privacy decision or response policy leaves the output DRAFT with a specific unresolved field. Do not invent 24/7 support or a response-time commitment.

Agree what the responder can do: inspect a scoped regression, route to the owning team, or execute an already authorized recovery step. A notification, issue assignment, incident declaration and operational mitigation are separate actions. Sentry can route notifications or create tickets, but delivery and a human response are additional evidence. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-alerts.html)

## 2. Define the measured signal

Record numerator, denominator, unit, exact query/data source, inclusive UTC interval, baseline interval, sample size, minimum volume, sampling/filter configuration, ingestion delay and exclusion reasons. Keep environment and release scopes explicit. Compare failures against eligible attempts from the same window and population. An error count alone is not an error rate; a retry can emit several events for one failed attempt. Affected users means distinct permitted identifiers, not event count. Sentry's affected-session percentage uses estimated project sessions and event count, so do not relabel it a verified checkout-failure percentage. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-create-alerts.html)

For latency, state the operation, duration unit and distribution statistic, accepted sample size, baseline and timeout treatment. Mean latency cannot substantiate a p95 threshold. Tail latency and unsuccessful attempts need separate inspection. If the selected monitor cannot express the required signal, preserve the signal contract and hand the missing measurement to the platform owner instead of replacing it with raw exception count. [Conceptual source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/google-monitoring.html)

If numerator and denominator use different sampling or exclusion rules, report the mismatch and withhold a population-rate claim. Do not divide sampled errors by total traffic or multiply by an assumed inverse sample rate. No-data, low-volume and delayed-data branches are inconclusive unless an adopted policy explicitly defines their response. Missing telemetry is not proof of recovery. SDK sample decisions and inherited traces can affect coverage. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-sampling.html)

## 3. Propose the rule and urgency

Use the owner's existing SLI/SLO and baseline where available. Record the source and approver for every threshold, window, volume floor, comparison, severity and response-hours choice. Separate page, triage ticket and informational feed by required response and urgency. No supplied policy means a draft recommendation awaiting review, not an activated rule. The [worked cases](../references/examples/actionable-alert-cases.md) illustrate decisions without prescribing production numbers.

Map the proposal to the actual selected Sentry surface: issue sources or connected monitor, environment, WHEN triggers, each IF qualifier, filters and THEN actions. Frequency and event-attribute filters only work with new-issue or event/activity triggers. Check the current form rather than assuming an escalation trigger obeys a count filter. Each IF/THEN block evaluates independently; overlapping blocks may perform multiple actions. Verify the installed integration and exact recipient destination without copying credentials. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-create-alerts.html)

Record the deduplication scope: Sentry throttles actions for a given issue, not a whole incident spanning several issues. Keep external incident correlation, acknowledgement, backup escalation and schedule resolution as separately specified and separately verified behavior. A latest-release-only filter can hide failures in older deployed releases; document the intended population before using it. Do not declare a problem solved because Sentry marks an issue resolved.

## 4. Bound sensitive data and sampling

Use Security's app policy. Allow only necessary metadata in the rule name, tags, message and evidence: environment, parameterized operation, release identifier, aggregate count/rate and controlled runbook link. Exclude credentials, cookies, auth headers, raw URLs/query strings, customer text and identifiers unless policy explicitly permits them. Internal IDs and hashes can remain identifying data. Inspect every notification action because it sends data to another destination. Avoid pasting real event payloads into reports.

Record error, trace and replay sample settings and known drop/ingestion limits separately. Do not increase capture, enable replay, unmask content or opt into bodies to make an alert easier to debug. Replay needs masking evidence with synthetic inputs, including portals, avatars/background images, dynamic text, forms and network data. Server scrubbing is a backstop for stored data, not proof nothing left the app. [Sensitive-data source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-sensitive-data.html), [Replay source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-replay-privacy.html)

## 5. Validate the draft and then authorized behavior

Review positive, negative, low-volume, absent-data, release/environment mismatch, repeated same-issue, simultaneous different-issue, privacy and recovery cases. State expected routing for each branch. A runbook identifies diagnosis, safe read-only checks, decision owner, any separately authorized action, rollback and what proves user recovery.

Only with explicit authorization configure or send a test. Record the precise destination, time, synthetic marker and observed receipt; redact private content. A test notification proves integration wiring, while real event triggers may behave differently. Separately record rule evaluation, schedule resolution, acknowledgement, escalation and recovery evidence. Do not manufacture these observations from a screenshot or worksheet. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/sentry-create-alerts.html)

For recovery, use fresh same-population telemetry meeting the adopted recovery threshold for its approved duration plus a successful journey check where authorized. Record open uncertainty when errors disappear through filters, sampling, quota loss or silence. Reconcile the Sentry issue and external incident separately. An owner reviews noise, missed signals and actionability using actual notifications and incident outcomes; no reduction percentage is promised. [Conceptual source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/sentry-stinger/references/research/actionable-alerts/raw/google-slo-alerting.html)

## Deliverable and proof labels

Return the completed worksheet, source-backed rationale, proposed rule mapping, case results and unresolved decisions. Distinguish DRAFT, source-reviewed specification, authorized configuration observed, notification delivery observed and operational recovery observed. None implies the next. Land application-specific reports in the existing monitoring report location from the Drone; source-forge evidence belongs in this enhancement's report folder. Follow Security, Quality and orchestrator Repository Health before any authorized commit or push.
