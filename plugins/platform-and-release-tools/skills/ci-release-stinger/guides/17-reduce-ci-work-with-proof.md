# 17: Reduce repeated CI work while keeping proof

Use when a team asks to make CI cheaper, faster or easier to trust. Start with guide 00 classification, then fill [the CI work and proof packet](../templates/ci-work-and-proof-packet.md). This is a source review procedure. A proposed graph proves neither actual speed nor a bill reduction. Governing research: [October digest](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/digest.md).

## 1. Establish the current candidate and baseline

Capture actual workflow files and invoked local scripts with file:line, triggers, selected platform/deploy producer, required check names/settings if readable, runner/toolchain, lockfile, build-time configuration fingerprint, permissions and resources. Record head SHA, base SHA, checked-out candidate SHA/tree and candidate kind: PR head, synthetic merge, merge group or release. If the checkout is dirty, record an explicit source-file manifest in addition to Git identity. Read labels as labels, not proof of the checkout that ran.

For each job record producer, consumers, unique proof obligation, duplicate installs/builds, resource creation/cleanup, duration/queue measurements, outcome, run/attempt and artifact identity. Different OS, toolchain, environment, migration baseline, secret boundary or feature settings may justify separate work. Do not collapse them just because commands share a name.

## 2. Propose the smallest graph change

Recommend one change at a time with a before/after obligation map. Build output reuse is eligible only when producer and consumer agree on candidate, inputs, platform/toolchain, configuration, dependency lock and artifact digest. A cache hit is an acceleration hint; it does not certify the candidate or replace the consumer check. Preserve existing security scans, tests, schema/migration checks and release contracts. Fewer jobs is not the success criterion.

Prefer extending an existing compatible job or consuming its qualified output before introducing another job. Split jobs when isolation, runner compatibility or measured feedback justifies the extra install/transfer/setup work. Record sequential critical path separately from the sum of runner time.

For a confirmed Vercel Git-integration app, identify its build/deployment and let Actions supply missing checks. An Actions build can be legitimate for a different environment or packaging proof. If an owner authorizes a CLI deployment model, the documented prebuilt path can upload an existing build, but changing deployment ownership/settings is a separate owner action. For another hosting platform, consult its existing specialist and current docs; do not force Vercel or Hivemind scripts onto it. [Vercel captures](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/vercel-github.html), [prebuilt](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/vercel-prebuilt.html).

## 3. Preserve trigger and required-check coverage

Map PR, production-branch push, merge-group if enabled, manual and deployment events separately. The required reporting path must fire for each admitted candidate even when an expensive job is deliberately omitted. A skipped workflow may leave its required check pending, while a conditionally skipped job may appear successful. A reporting job with `always()` still needs explicit failure/cancellation/missing-proof checks; unconditional success defeats the gate. [Syntax](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-workflow-syntax.html), [required checks](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-required-checks.html).

Path scoping needs a dependency/contract explanation, including shared packages, generators, configuration, lockfiles, workflow changes and test infrastructure. File extension alone cannot establish irrelevance. Uncertain relevance runs the affected obligation. A reduced quick pass may give early feedback; it cannot silently replace the agreed full gate. In a monorepo reuse its existing graph/tool rather than inventing a new path validator.

## 4. Bind preview, migration and artifact consumers

An e2e consumer records the deployment ID, immutable candidate URL, source SHA/config identity, readiness and isolated database baseline. A moving branch URL can test the next push. Verify the deployment event and target match the candidate before using a URL; an untrusted payload is not authority to send secrets or run arbitrary commands. Preserve deployment protection and approved test credentials. No temporary public bypass to make CI fast.

For migration checks, use the selected database owner's procedure for committed migration artifacts and isolated rehearsal. Do not generate a different production migration at merge time. Validate declared prerequisites, data safety, unique resource identity and cleanup/reconciliation even after cancellation. Prefer synthetic or approved non-sensitive data; a production data clone is not automatically authorized. Database URLs, tokens and secret-bearing env files never belong in job artifacts. Keep secret consumption in the appropriate trust-scoped job. [Artifact semantics](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-artifacts.html), [secure use](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-security.html).

Artifact consumers require successful producer conclusion, candidate/input identity and expected digest. GitHub's documented automatic digest mismatch is a warning, so it alone is not a fail-closed acceptance check. Use the target's existing proof/digest procedure. Missing, expired, mismatched or untrusted artifacts leave the obligation unproven.

## 5. Cancel and rerun deliberately

Use concurrency for obsolete speculative checks, scoped by workflow/candidate/resource purpose so unrelated work cannot cancel each other. Do not cancel an active migration/release merely because a newer check run exists; serialization and idempotency belong to that resource contract. Pending replacement and scheduling behavior are distinct from completion proof. Cleanup needs a surviving authorized reconciliation path, not an assumption that every cancelled job finishes its cleanup. [Concurrency](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-concurrency.html).

Reruns use the original event SHA/ref and original actor privileges. A targeted replacement may repair an isolated failed shard only when the checkout, input/toolchain/configuration, shard assignment, resource baseline and artifact acceptance remain equivalent. Retain passing evidence for every other required obligation and record the union explicitly. A changed candidate, generator, lockfile, migration ordering or environment invalidates relevant prior proof; execute the target's required combined-candidate procedure. Green on one shard, cancelled, queued or a wrapper's exit status cannot stand for the union. [Reruns](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-reruns.html).

## 6. Measure the proposal and close honestly

Measure cold/warm install and cache restore/save, queue delay, job/critical-path duration, failure frequency, retry work, artifact transfer/storage/retention, runner class, platform build time and resource lifecycle. Keep source, observation date, units and sample size. Account for cancelled attempts and fixed charges as well as passing runs. Monthly variable estimate is the sum of observed billed units times current applicable unit rates plus applicable fixed charges; runner minutes and wall time are different quantities. Unknown volume, billable units, rates or measurements make the corresponding cost/savings output Unknown. Do not fill unknowns with zero or invent vendor plan assumptions.

pnpm says caching may not help. Playwright recommends against browser caching. Start with fresh browser installation; use a browser cache only after controlled measurements justify it, keyed to the browser/toolchain compatibility and with system dependency installation retained. Keep untrusted cache writers apart from trusted secret-bearing jobs. [pnpm](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/pnpm-ci.html), [Playwright](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/playwright-ci.html), [secure use](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/ci-release-stinger/references/research/ci-efficiency-2026-10-07/raw/github-security.html).

Deliver file:line changes, obligation matrix, baseline/proposed inputs, observed outputs and uncertainty. Reuse existing local scripts and target proof tools; do not add a second CI validator merely for this workflow. Run Security, then Quality, then parent Repository Health. Commit, push, settings, paid resources, credentials, deployments and real CI/provider effects need the owner's specific authorization.
