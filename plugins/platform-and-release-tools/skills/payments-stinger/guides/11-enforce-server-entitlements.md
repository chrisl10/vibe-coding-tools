# 11. Enforce feature access on the server

Use for O275. First read [integration choice](01-choose-your-integration.md). The implementation owner remains SvelteKit 5 on Vercel with custom Elements; Next.js, React server code, native receipt validation and Connect require an explicitly qualified implementer. A UI component or another language skill alone does not supply one.

## Establish the integration contract

Complete [the worksheet](../templates/billing-access-contract.md) from the actual source and approved configuration evidence. Record exact installed `stripe` and `@stripe/stripe-js` versions, outbound API version, event endpoint version, snapshot/thin format, endpoint environment and owning Stripe account. An SDK cast does not validate a mismatched event shape. Keep secrets out of this record. Stripe documents immutable event shapes and version dependence in [current webhook research](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/webhooks.md).

Resolve the authenticated user to their authorized tenant, tenant membership/role and server-owned customer/subscription mapping. Match incoming account/environment and customer to that mapping before touching application state. Tenant metadata in an event is a correlation hint to verify against the mapping, not permission to select an arbitrary tenant. Unknown or ambiguous mapping is a quarantined incident with no grant. A signed event proves provider origin, not an application's tenant relation.

For every premium operation identify the server endpoint, background-job admission and data query enforcing the feature. The server authorizes tenant membership, action permission, entitlement, expiry and usage limit on every invocation. The UI reads a limited projection from this same policy and explains unavailable access; hidden buttons are no substitute for denied direct requests. Do not expose another customer's billing detail to explain a denial.

## Choose one feature authority

Record whether the product uses Stripe Billing Entitlements or an application-owned projection from subscription/invoice state. Do not have both independently grant the same feature. With Stripe Entitlements, map feature lookup keys to internal permissions server-side and list all active entitlements for the mapped customer. Summary events have a ten-entry limit; a truncated or failed page is not an authoritative empty feature set. Follow all pages before atomically replacing the projection. Product feature mapping changes may wait for the next billing period. [Provider entitlement source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/entitlements-api.md)

With an application-owned projection, declare the approved plan/product/price mapping, applicable invoice settlement, trial/paid-through/grace boundaries and downgrade behavior. Never accept the plan, amount, customer or paid-through time from browser parameters. Read the [state guide](12-separate-trial-payment-and-access.md) before granting paid access. [`active` versus payment source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/subscription-events.md)

## Make processing durable and replay safe

1. Read the exact raw request body and verify with the configured endpoint secret before use; never log the body, signature, secret or raw exception. Reject unsupported schema/version and mismatched sandbox/account scope. [Verification source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/webhooks.md)
2. For synchronous processing, use a database transaction that atomically claims the durable event key, locks/serializes the billing subject, changes the entitlement projection, inserts any authorized outbox jobs and records completion. A rollback must roll back both claim and local effects. A duplicate committed claim is a no-op; an in-progress claim is not proof of completed work. Delegate the concrete schema/constraints/isolation design to `db-wasp-drone`.
3. For asynchronous processing, verify and persist an inbox record or durable job before 2xx. A worker claims with a recoverable lease, commits projection plus outbox plus completed status together, and retries failed work. Do not send 2xx on an unpersisted in-memory task. A receipt row and a completion row represent different facts.
4. Serialize current-state refresh/recompute per mapped billing subject. Late snapshots must not overwrite newer state. Event creation seconds are not an object revision; equal timestamps and out-of-order deliveries are normal possibilities. A current read must use the correct account, environment and supported API version. If concurrent workers refresh, prove that an older refresh cannot commit after a newer one. [Ordering source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/webhooks.md)
5. Enforce semantic action idempotency as well as event dedup: one order fulfillment, one invoice-period access extension, one policy transition. Permanently suppressing every later `customer.subscription.updated` for the same object/type would drop real changes. Keep monetary ledgers separate from an idempotent feature-set replacement.
   Define retention and manual-replay bounds before pruning receipt/completion records. Deleting a dedup row must not make an old fulfillment repeatable; preserve semantic business-action evidence for the required lifetime. A provider's retry window alone does not define application audit or replay retention.
6. Reconcile after missed deliveries, page/read failure and recovery. Approved scheduled/read-only reconciliation enters the same serialized writer and audit path, never a browser return-page writer. Preserve the old projection with explicit freshness limits on failed refresh; apply the approved stale-state policy. [Reconciliation source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/entitlements-api.md)

External side effects cannot be made atomic merely by a local transaction. Drain an authorized outbox with a durable operation key, downstream idempotency where supported, observed result and recovery procedure. A crash after external success but before local acknowledgment needs result inspection. No exactly-once external-delivery claim follows from this guide. [API idempotency source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/platform-and-release-tools/skills/payments-stinger/references/research/billing-access-update/raw/idempotency.md)

## Required evidence before implementation qualification

Render cases for invalid signature, raw-body change, wrong tenant, unknown customer, wrong environment, duplicate ID, concurrent duplicates, distinct events for one fulfillment, equal timestamps, late old snapshots, database rollback, outbox crash/retry and page-two failure. Pair direct server requests with UI expectations, including revocation while the UI has an old session. Record actual test/build/runtime outputs on the target implementation. [Synthetic worked cases](../references/examples/billing-access-cases.md) are source reasoning only.
