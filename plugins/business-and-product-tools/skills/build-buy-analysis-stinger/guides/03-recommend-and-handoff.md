# Recommend one bounded next decision

Use the [worksheet](../references/templates/decision-worksheet.md), [fictional worked example](../examples/completed-decision.md) and [negative cases](../examples/negative-cases.md). This follows the small hard problem and lifecycle questions in purchasing guidance.

1. Reject suitability claims when an option fails a required behavior; keep UNKNOWN separate from FAIL. Do not score away mandatory security, ownership, accessibility, integration or exit requirements with low prices.
2. Present a three-column evidence comparison but make one recommendation. If required data is missing, recommend the single smallest decision-changing evidence task, not a purchase or invented winner. State its expected observation and falsifier, owner, permitted data, scope and status PLANNED / NOT_RUN. Preparing a trial does not authorize account creation, spend, credentials or execution.
3. For a supported provisional choice, state why it meets the requirements, uncertainties, conditions before commitment and what new evidence would reverse it. A source-based conditional recommendation is not procurement approval, product demand validation, a contract acceptance or runtime qualification.
4. Write the local advisory report to the agreed destination, or library/requirements/reports/build-buy-analysis/ when Library exists. Include scope/date, input provenance, evidence matrix, partial/comparable cost treatment, responsibilities, exit constraints, decision and unanswered owner questions.
5. Hand formal requirements to Library, decision records to ADR, platform choice to Infrastructure Fit, implementation to selected runtime owners and commercial/legal conclusions to their specialists. Do not create these downstream artifacts unless requested.

Source-component construction requires the parent's Security, Quality and repository-health review before an authorized commit or distribution claim. This skill's runtime performs analysis only.
