# Bound the sourcing decision

Read the [distillation](../references/research/distillation.md) and complete the first section of the [worksheet](../references/templates/decision-worksheet.md). This procedure adapts the needs/capability questions in [official purchasing guidance](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/business-and-product-tools/skills/build-buy-analysis-stinger/references/research/raw/purchasing.md).

1. Ask one compact batch for the user job, accepted requirements, decision owner, current system, volume, sensitive data, deadline, budget currency/period, supply options already considered and operational ownership. Missing inputs remain UNKNOWN. A fictional example supplies none of these for a real buyer.
2. Limit the comparison to one function with observable acceptance criteria. Separate must-have IDs, desired IDs and explicitly deferred behavior. Do not rewrite Accepted contracts. Hand unclear demand to Discovery before recommending construction.
3. Identify comparable approaches: bespoke internally developed, licensed service/product configured for the slice, and partner-delivered bespoke or managed integration. Reused open source can support any approach; it is not free staffing or proof of redistribution rights.
4. Match identical requirement IDs against every option. Distinguish supplier statement, current primary documentation, supplied dated contract/quote and authorized observation. Record version/plan/region/app category and passage or artifact locator. Unknown required behavior blocks a winning suitability claim.
5. Resolve related owners by catalog name through Pest Controller before dispatch. Source uses plugin-catalog.json; installed work uses trusted Core's explicit selected registry. A cached component is not selected. Missing related skills block only the conclusion that needs them.

Output a scoped decision question and evidence gaps. No accounts, trials, messages or tests against customer data are implied by preparation.
