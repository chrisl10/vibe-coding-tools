# Workflow guide

1. Load the installed `pest-controller-suit` Core skill and consult its roster before making any routing decision. This is the first instruction, always, no exceptions. Source work resolves component ownership from root `plugin-catalog.json`; installed work uses Core's explicit selected-plugin registry and resolver. Missing Core blocks routing. Load each selected pair's Stinger and required guides before work, and verify actual host tools/delegation. Cached files do not prove selection. Dispatch registered Drones at top level only when delegation is authorized; otherwise execute the selected paired procedure directly and report that fallback truthfully. No invented roles or nested dispatch.

2. Confirm the product outcome, users, data sensitivity, integration/payment paths, environments, operating constraints and the decision this risk assessment should inform. Treat supplied repository/documents as evidence, with date and provenance. Do not turn public observations into confirmed private behavior.
3. Route desirability/usability/feasibility/viability assumptions to discovery-research-wasp-drone. Separate observed facts, derived risks and unknowns. Give each material risk a concrete failure trigger, impact, existing evidence, owner, smallest validating check and decision needed; rank impact and uncertainty rather than inventing precise probabilities.
4. Use security-wasp-drone for an authorized code/architecture exposure review within its inspected stack remit. If there is no code, report design risks and missing evidence; do not claim a code audit passed. If the actual stack exceeds selected review coverage, name the gap and block the affected security conclusion.
5. Use estimation-wasp-drone to identify uncertainty in delivery and rework assumptions. Existing runtime failures, vendor deadlines and uncalibrated AI throughput remain explicit variables. Optional current market, operating-cost or legal analysis requires its actual selected specialist and fresh primary sources; do not fabricate a market study or legal conformance verdict.
6. Have library-wasp-drone record risk-driven acceptance criteria and contract-writing-wasp-drone identify disputed shared authority/data/event terms. Keep accepted agreements unchanged; affected Draft boundaries remain blocked until exact revision acceptance.
7. Deliver a ranked risk register, unknowns, evidence limitations, recommended next validation action, owner map and go/provisional/blocked decision for the stated outcome. Observational risks are not a legal-compliance determination. This assessment changes no product settings or provider resources.

## Inputs and host qualification

Use trailing invocation text exposed by the actual host; `$ARGUMENTS` is supported only where documented. Reuse answered inputs and accepted decisions. Ask one concrete batch for unresolved material inputs before dependent work, while continuing independent authorized work. Claude/Cowork uses the owner flat command, Cursor its generated command projection, and Codex the owner's generated `source-command-assess-product-risk` skill. Source generation is not installation, role discovery, or runtime proof. Resolve all resources against the selected carrier root. A missing required owner blocks its dependent boundary and is named in the report; optional branches require only their own selected dependencies.

## Output contract

Report status, selected owner/version and paired procedure, concrete artifacts, accepted contract pins, actual checks and their results, evidence limits, unfinished boundaries and the smallest unresolved user decision. Keep source/static checks, mock/browser behavior, native execution, packaged artifacts and provider evidence separate. Permission to create a source workflow does not authorize installation, provider writes, credentials, spend, commits, push or publication.
