Protocol compliance does not authorize an action.

## Establish the executor boundary

1. For every callable operation name the human task, principal, tenant, recipient, resource, action and limits. Record the trusted authorization source and expiry/revocation behavior. A broad tool description, delegated agent, schema-valid argument or retrieved approval claim does not expand this scope.
2. Separate draft/read/propose from commit/send/publish/delete/spend. Show concrete target, payload and consequences when the user's existing approval does not cover the action. Reuse valid task-specific approval; do not add repeated prompts for the same unchanged authorized action. A changed recipient/resource/action/budget requires fresh scope assessment.
3. The executor validates complete arguments, principal and current resource authorization independently of model output. Derive tenant/user identifiers from trusted context; do not trust model-selected IDs. Enforce destination/resource allowlists, URL/redirect policy, field-level limits and result bounds in the relevant backend. Security owns SSRF/credential/leak testing; MCP protocol owner owns protocol design.
4. Set per-task model/tool steps, time, cost and concurrency budgets with explicit exhaustion behavior. Account for pending and unknown effects. Reject parallel effects that violate ordering or share mutable state without the host's consistency contract. An agent may return partial results with reasons; it may not silently claim all tools succeeded.
5. For retryable effects, bind a durable operation identity to principal, action and canonical payload. Atomically reserve/record attempts in the host's chosen store. Same ID/same payload returns the known result; same ID/different payload conflicts. Do not substitute an LLM tool-call ID, process-local set or schema field for durable idempotency. External providers must support the contract or the workflow reconciles their observed state before retrying.
6. Recheck permission at commit, including revoked membership, expired approval and changed draft version. For multi-step writes record each step's real status. Use the approved transaction/outbox/workflow contract where available. Compensation is an additional effect requiring its own scope; do not auto-refund or undo merely because a later step failed.
7. Normalize errors without hiding them: malformed request, denied authority, conflict, budget exhausted, dependency failure, cancelled, partial and unknown effect. Preserve tool/protocol error distinctions. Unknown after timeout is not failure or success. Read back using the bounded resource identity before any retry; if reconciliation cannot establish status, escalate with evidence.

## Review actual behavior

Fill [the effect worksheet](../templates/tool-effect-review.md). Run authorized synthetic tests for allowed draft, wrong recipient, cross-tenant ID, document-origin approval, approval revoked before commit, repeated same operation, changed payload under same ID, concurrent duplicates, timeout after provider commit, partial multi-step completion and budget exhaustion.

Record actual proposed call, executor decision, durable state and external effect proof separately. A valid JSON proposal proves format only. A mock denied result proves that mock only. Production credentials/effects are excluded unless specifically authorized. Hand findings to Security and the owning integration/payment/backend specialist; preserve the existing provider engine.
