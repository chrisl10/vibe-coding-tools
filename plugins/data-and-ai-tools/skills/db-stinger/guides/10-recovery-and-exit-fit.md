# Recovery and exit qualification

Read primary digest. Source-file preparation is distinct from restoration/provider writes.

1. Define acceptable recovery point and recovery time with the owner, data classes, regions, retention and actual business continuity dependency. Record goals as requirements, not vendor guarantees. Identify database rows, uploaded objects, auth/session configuration, search projection, queue state and operational secrets by purpose, never values.
2. Verify what each provider backup includes, where it is retained, available restoration targets and downtime behavior. Supabase database backups exclude Storage API object bytes; a database restore alone cannot meet an uploaded-file recovery goal. For every candidate, record restore rehearsal evidence, date/size/config and untested boundaries.
3. Draft an authorized isolated rehearsal: known fixture manifest, database row/constraint/policy checks, object checksum checks, auth/permission checks and consumer continuity. Existing credentials, source/provider restoration, paid capacity or any live action requires applicable explicit approval. A backup toggle or successful snapshot is not a restore test.
4. Inventory exit dependencies beyond SQL: extensions/versions, auth identities/session migration, buckets/object URLs, realtime subscriptions, edge jobs/webhooks, egress rate/volume, backups, DNS/endpoints and privileged roles. Owner-approved additive cutover/reconciliation criteria are required; no guessed data backfill or destructive cleanup.
5. Deliver coverage by stateful service, exact RPO/RTO target versus observed evidence, recovery blockers, export/reimport scope and rollback trigger. Library records requirements/ADRs/contracts; DB writes the approved schema/migration slice, operators implement approved execution, Security precedes Quality. No failed rehearsal is silently replaced by a vendor promise.
