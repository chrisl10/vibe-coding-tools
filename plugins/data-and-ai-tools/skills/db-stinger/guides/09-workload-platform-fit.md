# Workload-led managed PostgreSQL choice

Read [current digest](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/data-and-ai-tools/skills/db-stinger/references/research/2026-10-data-fit/distilled.md) and [worksheet](../templates/platform-fit-decision.md). The older platform matrix is a historical snapshot; do not copy its versions, categorical service gaps, prepared-statement claims, uptime figures or price assumptions as current facts.

1. Read existing schema, recent migrations, runtime/client/ORM, actual Postgres/provider metadata and non-secret architecture. Do not connect to a live database, expose a connection string or run EXPLAIN ANALYZE against production merely to choose a provider. Ask only for missing material constraints.
2. Normalize workload: tenant/account rows and growth, transactions/write contention, hot query patterns, concurrent client connections, serverless bursts, long-lived sessions/LISTEN needs, background jobs, extension requirements, storage objects/egress, realtime fanout/message rates, region residency and user latency. Separate measured, forecast and unknown inputs; do not invent throughput from users.
3. Inventory platform services individually: identity/session/orgs/SSO, Data API/RLS, object storage/CDN, Realtime, functions/jobs and backups. Supabase integration is a fit when its verified services cover the accepted requirements. Neon now documents managed authentication; inspect its current implementation and limits rather than asserting no auth. For managed Postgres elsewhere, verify actual product/engine/extensions/region/network and identify each ancillary service owner. A common database engine does not imply common application service behavior.
4. Match connection modes to runtime and workload. Confirm session-state/prepared-statement/transaction semantics, IP/network reachability, client pool limits and migration/restore connection needs from current official docs. Supabase transaction pooling does not support prepared statements in the captured guide. Read existing DB pooling procedure, and route Neon driver/branch/Drizzle details to neon-drizzle-stinger. Do not copy a vendor endpoint or port template as a secret-bearing configuration.
5. Require identity/tenant policy design and denial evidence at actual data/API paths. Client Data APIs require their documented RLS model; server-only access needs accepted actor/tenant authority and privileged-role isolation. DB owns schema requirements; auth owns identity; Security audits enforcement. Private realtime rooms require their own authorization and revocation checks, not a successful database read alone.
6. Compare cost shapes using dated owner-supplied quantities and current official rate sources: database compute/storage, backups/PITR, replica/branch use, auth/SSO, object storage/CDN/egress, realtime/fanout, queue/functions, networking and operator time. Missing rates stay unknown. Select operating-cost-stinger only if installed and cost modeling is requested. No universally cheap provider or free idle workload claim.
7. Recommend one platform against must-have constraints, explain counterevidence and a concrete validation spike. Region/plan/version/extension/recovery unknowns can make the decision provisional. Use [recovery and exit](10-recovery-and-exit-fit.md) before calling it production-ready. Do not provision, install, alter flags, migrate or switch a provider through an advisory selection.
