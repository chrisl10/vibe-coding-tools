# Evidence-led Postgres vectors versus Qdrant

Read current primary digest, then the existing principles and store-specific schema/index procedures. Treat old fixed vector-count thresholds and isolated benchmark numbers as dated secondary context, never automatic migration triggers.

1. Read actual store/schema/extension versions, embedding model/dimension/distance, source records, tenants/visibility, corpus size/chunks/update/delete rates and query/filter distribution. Capture workload growth as forecast, not measured data. A multimodal label does not establish compatible text/image embeddings or a need for another store.
2. Normalize search objectives: top-k, required relevance/recall metric, p50/p95/p99 latency, concurrency, write/backfill load, freshness, deletion/revocation latency and budget/operator capacity. Keep missing inputs explicit. Agree thresholds with the product owner; do not invent a success budget to make one engine win.
3. For Postgres, evaluate exact search on the filtered subset and the actual approximate index/operator plan. Current pgvector has documented filtering, iterative-scan and partitioning options; confirm the installed extension before suggesting them. Route relational schema/pool/plans to DB, vector index/storage to this pair. Do not run the existing perf SQL against a live system without authorized execution scope.
4. For Qdrant, verify current payload indexes/filter syntax, collection/vector representation, sharding/replication, read/write consistency and ordering against the accepted workload. Preserve the cost/operator/backup/restore burden of another stateful service. Its payload filter is not application authorization by itself; tenant/actor scope must be accepted and denial-tested.
5. Have retrieval-stinger own the fixed labeled evaluation corpus/golden-query set and before/after metrics. Embeddings-runtime-stinger fixes model/dimensions/input preprocessing; this pair proposes storage/index settings. Compare same corpus snapshot, model, relevance labels, tenant filters, top-k and query mix. Separate exact identifiers, paraphrases, sparse/hybrid and each modality. Report latency with hardware/region/cache/index/build/update configuration, sample size, known limits and query errors. No invented benchmark.
6. Recommend one store or retain the existing store with a scoped validation spike and explicit counterevidence. A dedicated Qdrant collection may isolate search contention while Postgres remains relational truth; this is not automatic migration of every table. Missing recall/latency/filter distribution can leave the recommendation provisional. Use [projection contract](02-projection-consistency-and-eval.md) before adopting a split.
