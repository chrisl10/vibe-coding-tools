# Bound one customer operation and every attempt beneath it

Use this for “limit agent tokens”, “budget retries”, “cap fallback spend” or “keep one slow request from running forever”. Complete the [contract worksheet](../templates/request-budget-contract.md). Source basis: digest.

1. Name operation, tenant, feature, admission owner, contract version, currency, approved spending authority and window. Keep monthly money, per-operation attempts, concurrency, token ceilings, output, tool calls and wall-clock latency separate. A user asking for research or advice has not approved paid execution. Host/model settings remain inherited.
2. Enumerate the call graph: primary request, SDK transport retries, application retries, gateway retries, fallbacks, tool/provider operations and continuation loops. Record bounded maxima and who owns each. Retries at multiple layers can multiply. Count failed/timeout/partial stream attempts and unresolved invoice status, not just successful answers. Never retry a spend-cap failure as a transient 429 automatically; classify the actual provider error and billing terms.
3. For each permitted attempt, bound prompt including tool results/history, billable reasoning/output tokens where applicable, provider request bytes, output tokens, tool iterations, end-to-end deadline and retry delay. Enumerate model/version/provider/region/plan and fallback order. Choose a fallback only after Mind's task-specific quality acceptance, schema/tool compatibility and Security's data-boundary review. No unlimited “try another model”.
4. Map uncached input, cache creation, cache read, output and separate tool/storage/retrieval units to dated supplied rates. Use guide 08 to resolve selected Software Economics owners and reuse their calculators for supported complete monthly scenarios. Unknown rate or nonlinear pricing blocks numeric money conclusions. Missing cache hits reserve the miss/write case; a response cache hit must still satisfy freshness, tenant isolation and tool-side-effect semantics.
5. Propose atomic admission and reservation across workers: ledger owner, idempotent operation/attempt identities, tenant/feature/global scopes, available balance minus existing reservations, lease ownership and recovery, concurrency limit and stale reservation handling. Reserve permitted worst-case billable attempts before dispatch; deny or queue when money, tokens, attempts, concurrency or remaining time are insufficient. Queueing itself consumes deadline and needs a bounded length/expiry. A worksheet does not implement these controls.
6. Reconcile each attempt using actual usage and provider request ID where supplied: reserve, dispatched, response/partial/timeout, settled amount, unreconciled amount and released amount. On timeout, cancellation or worker death, do not release money merely because the client stopped waiting: provider processing/charging may continue. Duplicate callback or late result must not release twice. Keep uncertain cost reserved under an explicit reconciliation policy; invoice delay and overshoot need quantified allowances before a hard-control claim.
7. On exhaustion, emit the approved degraded response or human handoff with remaining uncertainty. Never silently buy credits, raise limits, change models/settings, drop required safety checks or return a lower-quality answer as if accepted. Implementation owner plus Security must exercise concurrent reservation, cache miss, retry multiplication, duplicate settlement, cancellation, stale worker, late invoice, long output, tool loop and quality-failing fallback before enforcement is claimed.
8. Deliver contract, call graph, supplied-rate scenario references, unresolved facts and observed proof status. Rate limits, dashboards, alerts and an SDK token argument are distinct from end-to-end financial enforcement. Re-evaluate when rates, SDK/gateway versions, model billing, call graph or quality requirements change.

Work the [cases](../examples/request-budget-cases.md) without making a provider call. Mind owns orchestration/evaluation and implementation owners own runnable application controls; this pair owns provider facts and budget qualification.
