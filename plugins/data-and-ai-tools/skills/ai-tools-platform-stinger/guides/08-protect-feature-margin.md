# Protect an AI feature's margin before increasing usage

Build a complete usage ledger and qualify the selected spend controls before claiming the feature can support its customer price.

1. Confirm feature, billed customer unit, currency/period, accepted pricing and refund/payment assumptions, provider/model/version/region/plan and data-egress boundaries. Identify observed versus hypothetical workload. Unknown rate, currency, fee or failure billing terms block the dependent monetary total; never replace them with zero.
2. Record each operation's successful, failed, retried and fallback attempts separately. Reconcile token usage by uncached input, cache creation/write, cache read, output and any provider-specific billable units. Keep successful customer operations distinct from provider attempts. Avoid counting cached input twice or applying a cache discount to output/uncached input.
3. Inventory retrieval queries, embedding/index/backfill tokens, rerank calls, tool/provider operations, storage GB-month, network GB, fixed plan floors/gateway fees, observability and paid operations labor. Confirm allowance/shared-credit/floor ordering from the actual contract. Explain exclusions such as tax, FX, tiering, invoice rounding, data-retention or refund rules instead of hiding them.
4. Model low/base/high and downside assumptions, including failed/retried calls, cache misses, long outputs and expensive fallbacks. Record peak requests/tokens/concurrency separately from monthly volume. State the reserve method, measurement window, in-flight reservation and overshoot allowance; a rate limit or alert is not a proven hard spend cap. Never invent a margin percentage when revenue/rates are missing.
5. For installed feature-margin arithmetic, first run trusted Core's `hooks/resolve-component.py ai-tools-platform-stinger --kind skill --workflow feature-margin-economics` through host tools, using the actual resolved Core path. This registered workflow requires selected `software-economics-tools`; a missing selection stops dependent arithmetic and is a handoff gap, never permission to load an unselected cache. Then resolve Software Economics `operating-cost-stinger` and `unit-economics-stinger` individually through the selected-owner resolver. Source work instead uses the catalog's canonical `source_root`. Reuse their field contracts, worksheet templates and bounded offline calculators for complete authorized inputs; do not implement another arithmetic helper. Classify cost-of-revenue versus operating costs explicitly. Unsupported nonlinear rates need a disclosed worksheet extension rather than flattening an invoice silently.
6. Propose a bounded control contract: per-tenant/feature admission, request/output/tool limits, maximum retry/fallback chain, explicit in-flight budget reservation/reconciliation and an approved degraded response. Preserve application correctness and quality acceptance; a cheaper fallback must pass the feature's actual evaluation. These are proposed product controls until the implementation owner and Security qualify them.
7. Compare the ledger with provider usage/invoice evidence only when supplied and authorized. Keep credential values out of artifacts. Test control behavior using authorized fake fixtures first; actual alerts/caps, queues, retry behavior and final revision need observed proof. Installing providers, changing billing/caching settings, buying credits or altering customer prices remain task-specific owner actions.
8. Deliver usage/rate/evidence ledger, cost scenario outputs where complete, unresolved inputs, control proposal and one next decision. Do not describe a scenario as an observed bill, margin or realized saving.

Grounding: update digest. Mind owns feature architecture/evaluation, platform owns provider facts, Software Economics owns arithmetic, Security owns independent authorization/secret/control review.
