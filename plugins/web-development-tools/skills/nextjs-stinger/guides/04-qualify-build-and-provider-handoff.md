# Qualify build and provider handoff

1. Inventory existing scripts and dependencies, Node/TypeScript versions and lockfile. Use the project's installed commands; obtain owner approval before installs or configuration/provider mutations. Current docs list Node 20.9 and TypeScript 5.1 minima, but the selected version and provider may constrain them further. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/web-development-tools/skills/nextjs-stinger/references/research/raw/installation.md)
2. Run the app's existing typecheck, lint, integration and production build. Next 16 build does not run lint. Preserve exit codes and artifacts. Do not call a static parser check a Next build. Do not run Next when it could auto-install missing TypeScript dependencies without authorization. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/web-development-tools/skills/nextjs-stinger/references/research/raw/installation.md)
3. Run the built app locally with existing dependencies and perform guide03's production request cases. Record exact source revision, build config, route output classification and evidence. Missing runtime/dependencies means NOT_RUN, not pass.
4. Give selected provider owner the output mode, server/action requirements, Node/Edge compatibility, cache store and instance topology, image/asset needs, environment variable names only, and preview/production separation. Static export cannot serve server-required private actions; verify adapter feature support rather than assuming parity. Deployment remains a distinct authorized action. [Source](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/web-development-tools/skills/nextjs-stinger/references/research/raw/deploy.md)
5. Send framework audit to nextjs-security plus Core Security. Run Security then Quality; parent runs repository health. Record unresolved findings and obtain authorized commit/push approval. Provider readiness and an app build are separate from an actual deployment result.
