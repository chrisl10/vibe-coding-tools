# Implement locale routing and resources
Grounding: [W3C language](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/web-development-tools/skills/localization-stinger/references/research/raw/w3c-language.html), [Intl guide](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/web-development-tools/skills/localization-stinger/references/research/raw/mdn-intl.html), [ICU messages](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/web-development-tools/skills/localization-stinger/references/research/raw/icu-messages.html).

1. Read the target's framework, route convention, existing message engine, rendering boundaries and UI context. Record supported locales, explicit default, fallback order, source-language ownership, route/cookie preference precedence and persistence authority. Ask for missing product decisions before dependent implementation. Do not add a framework or message dependency by assumption.
2. Implement within the selected router and installed resource loader. Canonicalize language tags, then map only approved supported tags. Never interpolate user locale input into a file path, dynamic import, remote URL or filesystem lookup. Unsupported input follows the agreed fallback or explicit rejection. Locale selection grants no authentication or tenant capability.
3. Define stable semantic keys, whole messages, translator context and named placeholders. Preserve routes and form state when changing language; preserve authorization checks, tenant cache separation and redirect allowlists. Server render and client hydration must use the same resolved language/resource version. Do not infer account identity from a locale preference.
4. Validate resource key parity, missing keys, intentional fallbacks and placeholder parity. Build a missing-key behavior suitable for the target; do not ship empty labels or raw keys silently. Translation resources and interpolation are untrusted text. Render via text nodes or the framework's escaped binding. Rich markup needs a separate approved component schema and Core security review; never enable raw HTML as a localization shortcut.
5. Record translated public content versus private/user content. Do not upload content to translation services, log messages/PII or enable a provider without the user's task-specific authorization. Keep schema checks separate from translation quality review.
6. Exercise the target router and rendering boundary using available project tests. The framework-neutral example is a constructed exact-match allowlist, not Accept-Language negotiation or a server integration.

Deliver resolved locale precedence, changed paths, resource checks and actual route/hydration proof. Where the runtime was not exercised, state NOT_RUN.
