# Choose Tailwind and component primitives

Use this procedure for “Should I use Tailwind and shadcn for this app?” Deliver a completed [fit worksheet](../references/component-fit-intake.md) and one recommendation with evidence. This is framework intake, not a UI implementation.

1. Read actual package versions, framework entry files, CSS entry and supported-browser requirements. Preserve the working stack unless the requirement justifies a change. If the browser requirement conflicts with current v4 support, stop the v4 recommendation and record the mismatch. Compatibility archive
2. Separate styling, behavior and product decisions. Tailwind supplies utility styling. A primitive library supplies interaction foundations. Copied shadcn components become source you maintain. A design system defines product tokens, composition and usage rules. Selecting one layer does not settle the others. Svelte source model, React source model, Bits foundation
3. Match the component variant to the existing framework. Svelte 5 goes to selected shadcn-svelte and Svelte owners. React shadcn questions go to React, modal/toast/dialog and icon owners for their respective boundaries. Verify those owners are selected before dispatch. For Vue, Nuxt and Next.js, verify `vue-stinger`, `nuxt-stinger` and `nextjs-stinger` are selected; this guidance does not create a missing implementer. Route actual UI work through Impeccable, with design-system or product UX owners governing tokens and surface rules.
4. Inspect class detection before blaming component rendering. Use complete literal class variants, never a string such as `bg-${color}-600`. Register ignored external component source with `@source` relative to the stylesheet. For monorepos, record the scan base and relevant package paths. Do not blindly scan all node_modules or safelist every class. Detection archive
5. Map reusable tokens using `@theme`; use ordinary CSS variables for values that do not need utilities. When referencing another variable, assess its scope and the documented `inline` behavior. Token names and colors still belong to the product owner. Theme archive
6. Declare the theme contract. System preference, class selector and data attribute are different choices. Selector-driven dark mode needs its matching `@custom-variant`; theme persistence and SSR initialization belong to the framework/theming owner. Check first response, hydration and navigation under each supported preference. Dark archive
7. Define actual acceptance checks. Run the consuming app's build with existing tools; inspect generated CSS for each representative variant and imported component package. Verify server render/hydration if applicable. Exercise dialog opening, initial focus, keyboard containment, escape and focus return as applicable to the chosen component configuration; check accessible names, disabled/error states, contrast and zoom. Bits documentation provides behavior APIs, not proof about customized app output. Dialog archive
8. Report source qualification separately from app execution. Include update ownership, upstream revision and retained license notices for copied source. Unknown license compatibility needs the relevant dependency/legal review. Do not execute install or overwrite commands merely because a recommendation names a package.

Examples: [worked cases](../references/component-fit-worked-cases.md). Grounding: distillation.
