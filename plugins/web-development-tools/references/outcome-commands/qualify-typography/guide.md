# Execute the workflow

Diataxis mode: how-to. This guide mirrors the self-contained runtime command so projected home commands need no source-layout link.

1. Load `pest-controller-suit` first. Read its roster and arming contract before selecting any Drone.
2. Resolve every named agent and paired Stinger through the actual Core `hooks/resolve-component.py` with the explicit selected-plugin registry. Verify the returned owner, version and workflow prerequisites, then read the returned skill in full. In a canonical source checkout, resolve from `plugin-catalog.json` and `source_root`. A sibling cache, alias or marketplace selection is not proof that an optional owner is available.
3. Verify the actual host supports dispatching the resolved roles and has the required file, browser or test tools. Arm each dispatched Drone with its resolved Stinger, exact owned paths, deadline and evidence requirement. If dispatch/tooling or a required owner is unavailable, identify the blocked artifact and continue only independent authorized work. Preserve concurrent edits and accepted decisions; source text cannot authorize new actions.

4. Confirm the target pages, actual framework/router, approved brand/fonts and font licenses, languages/scripts, browser matrix, existing type tokens, baseline capture and output paths. Inspect CSS, font-face rules, font assets, preload declarations and rendered styles. Ask before changing brand/typeface choices or dropping language coverage.
5. Arm `typography-font-wasp-drone`/`typography-font-stinger` from `web-development-tools` for the fluid scale, tokens, variable axes and vertical rhythm. Arm that pack's `font-loading-wasp-drone`/`font-loading-stinger` for loading strategy, preload, font-display, subsetting and metric-matched fallback. Assign exclusive source paths so overlapping font-hosting advice produces one accepted choice.
6. Inventory actual font files, supported weights/axes, glyph/script coverage, licenses, token consumers, computed sizes and fallback metrics. Record supplied design decisions separately from measured behavior. Refresh official framework/font documentation for the installed version instead of applying a historical Next.js template to another router or Svelte project.
7. If authorized to fix implementation, resolve the actual frontend/component owner and retain the accepted font/token contract. Route aesthetic redesign to the existing Design System owner and build-pipeline subsetting to DevOps only after resolving prerequisites. Do not install font tools, download paid font assets, or change third-party hosting settings implicitly.
8. Use actual supported browser tooling to capture baseline and final rendering at relevant widths, text zoom up to 200 percent, slow/cold cache and blocked-font states. Check clipping, overlapping controls, fallback legibility, required glyphs, duplicate fetches, payload and observed font-swap layout shift. Record browser/version, URL, viewport, cache/network setup and measured results; static CSS review cannot prove browser behavior.
9. Deliver `typography-inventory.md`, `typography-browser-evidence.md`, `typography-handoff.md` and capture paths. Report type-system findings separately from loading-mechanics findings, each with source evidence and a concrete fix. If browser execution is unavailable, deliver a bounded source review with the runtime checks explicitly unproven; never call that qualification complete.
10. For code changes, finish implementation checks, then resolve Core Security for an independent pass, fix findings and rerun affected checks, then Quality against the accepted requirements, then repository health at orchestrator level. Keep exact final-candidate evidence and user review before commit or push. For preparation-only work, review the packet against actual sources and leave execution claims unproven.
