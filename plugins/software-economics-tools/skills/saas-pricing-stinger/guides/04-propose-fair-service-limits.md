# Propose limits from value and usage evidence

For O281 use the selected Unit Economics owner's [fair-limits guide](../../unit-economics-stinger/guides/04-fair-service-limits.md) and [integrated worksheet](../../unit-economics-stinger/references/templates/fair-service-limits-worksheet.md), resolved through trusted Core for installed work. Its dated source digest supplies documented meter/access/credit distinctions. Reuse that owner's arithmetic once.

1. Collect buyer/job, included feature, usage unit/window/aggregation/sharing and current accepted policy. Connect the cost driver to the buyer's value metric; if they differ, explain the predictability and legitimate high-use tradeoff. Do not select a report/token/storage threshold from account-month cost alone.
2. Read the cost, baseline, legitimate high use, suspected abuse and incorrect-blocking rows. Propose one provisional allowance/limit and readable overflow behavior only when supplied units, value and policy inputs support it. Otherwise the amount stays Unknown and the recommendation is to obtain the missing decision evidence.
3. Record warning, overflow cost/action, recovery/reset, appeal/review and owner-selected fairness criteria in the same entitlement card. Preserve original accepted policy separately. Criterion choices and acceptance thresholds belong to the owner; economic feasibility does not establish fairness or willingness to pay.
4. Link the exact evidenced owner decision, source/date/authority and permitted scope. Without it mark the proposal unaccepted. Route separately accepted entitlement/billing implementation to selected Payments, and separately authorized abuse controls to the actual selected Security/platform owner. Unknown availability remains a handoff gap.
5. Deliver one provisional recommendation/reason, counterevidence, unknowns, static arithmetic result and each proof boundary. No price, billing, rate limit, flag, refund, provider or customer-contact action is authorized by the worksheet. Actual billing, legitimate-user behavior, fairness/customer acceptance, abuse effectiveness and native execution remain NOT_RUN until separately observed.
