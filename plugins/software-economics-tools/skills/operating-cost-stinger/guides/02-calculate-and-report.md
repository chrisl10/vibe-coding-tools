# Calculate and report

1. Fill the [input template](../references/templates/input.json) with complete dated low/base/high assumptions and the [worksheet](../references/templates/worksheet.md) with evidence for each meter. Do not choose architecture or change a vendor plan.
2. Confirm the generic credit/floor order in [the model](../references/model.md) matches each actual invoice. If it does not, use a disclosed manual extension instead of reporting calculator output as that provider's bill.
3. Run `python3 -B -m scripts.calculate --input references/templates/input.json` from this skill directory. JSON goes to stdout; input is one explicit local file. No remote calls, output-file writes, credentials or installed dependencies are needed.
4. Reconcile gross usage, unit allowance deductions, credit allocations, floors, additive fees and unused credit. Compare low/base/high and identify the meter that drives the difference. Basis: Vercel, Railway, Supabase.
5. Deliver monthly provider cash, paid labor cash and separate unpaid time valuation. Explain excluded taxes, invoice timing, tier/proration/rounding behavior and unpriced dependencies. Supabase's billing-cycle guidance supports keeping invoice timing distinct from a month estimate: raw source.
6. Recommend the highest-impact workload or rate to measure next, with one reason. If the user wants a feasibility margin, resolve Unit Economics through Core's selected-owner resolver and hand off dated costs. If they want deployment or cost-control configuration, resolve the selected platform owner and preserve its approval boundary.
