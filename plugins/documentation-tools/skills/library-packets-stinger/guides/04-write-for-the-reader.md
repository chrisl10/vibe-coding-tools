# Write for the reader

1. Give every document one reader and decision. Lead with the supported conclusion or useful explanation. Use the [brief structure](../references/brief-template.md) as a starting point, not a compulsory set of headings.
2. Write ordinary explanations at an eighth-grade level. Use familiar words, concrete examples and connected paragraphs. Engineering documents may retain needed technical detail. Remove em dashes, padding, buzzwords, repeated caveats and explanations that do not help this reader.
3. Use a single chosen analogy only when it helps. Clearly distinguish illustrative scenarios from observed customers or results. Do not invent statistics, prices, deployment, capabilities or testimonials.
4. Attach claim IDs to the manuscript's material factual units. Complete a semantic evidence review: check that the source passage supports the actual claim, actor, scope, status, date and comparison. An exact quote match is only a mechanical check.
5. Review public prose separately. Explain approved outcomes and meaningful user choices. Exclude internal code, topology, flags, schemas, private names/paths, sensitive prices, security detail and roadmap weaknesses. Keep full evidence private and use approved public-safe source aliases where appropriate.
6. Generate the audience's citation list from the same accepted source/claim map. No private path or internal title belongs in the public folder. Record unresolved public permission before export; do not guess it from source text.
