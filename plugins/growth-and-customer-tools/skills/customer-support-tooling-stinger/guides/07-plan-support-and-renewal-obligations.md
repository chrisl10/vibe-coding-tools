# Plan support and renewal obligations before selling

Load this guide before proposing customer support promises, renewal terms or offboarding expectations. It takes precedence over historical numeric examples in the SLA, inbox and founder guides. Use the [worksheet](../templates/support-renewal-obligation-worksheet.md). Grounding: distillation.

## 1. Establish the offer and actual obligations

Ask for team size, B2B/B2C posture, channel, conversation volume and AI requirements before tool recommendations. For an obligation-only task, also collect offer/version, intended users/timezones, existing customer promises, customer-facing and contractual documents, approval owner, staffing and supplied cost inputs. Keep missing inputs UNKNOWN. Planning can proceed with gaps; approval cannot be fabricated.

Create one row for each exact promise with source and status. Distinguish a marketing sentence, negotiated agreement, internal target and provider policy. Preserve contradictions and route them to the controlling owner and qualified reviewer. Do not let an internal or vendor target silently become a customer guarantee. Intercom's own policy illustrates that targets and guarantees can differ. Policy archive

## 2. Specify each clock and calendar

Write impact-based severity triggers, intake channels, named primary/backup, IANA timezone, working days, holiday/DST handling, leave cover and a staffed escalation channel. Define first meaningful human response, next update, mitigation, resolution and availability separately. Define exact start and stop events plus snooze/customer-wait/reopen semantics. An acknowledgement is not a resolved defect. The selected platform must support the required object/metric and behavior; provider definitions differ. Intercom SLA archive, Plain concepts

Reject a 24/7 or fast-response proposal when no matching staffed coverage and backup exist. Slowing a numeric target alone does not create coverage. A phone notification, inbox setting or AI agent is not an accepted on-call rotation. Ordinary triage windows cannot simultaneously satisfy a shorter continuous clock. Record every uncovered interval; do not promise a fix deadline controlled by an unknown upstream vendor.

## 3. Price the work using supplied inputs

Calculate period demand, handling capacity and labor/tool/reserve cost from the worksheet. Include maintenance, incident reserve, renewal/offboarding, documentation and customer follow-up. Show assumptions and sensitivity to doubled arrivals or an absent primary. Compare peak arrivals and clock feasibility separately from average monthly capacity. If volume, handling time or rate is absent, output the formula and UNKNOWN result. Never invent a vendor price, loaded labor rate or deflection benefit. The arithmetic is our planning method, not a vendor benchmark.

## 4. Bind lifecycle duties to owners

For renewal: record offer version, renewal date/timezone, auto-renewal choice, notice deadline/channel, changed terms/price acceptance and the person maintaining the calendar. Qualified review decides applicable terms and notice requirements; this guide supplies no jurisdictional rule.

For cancellation/offboarding: specify request receipt, effective billing end, last charge, access/entitlement cutoff, remaining support, export window and retention/deletion separately. Capture outstanding usage/refund/credit questions for Payments and the owner. Stripe's cancellation docs describe different timing and events, so a request receipt cannot substitute for effective cancellation or application-access proof. Stripe archive

For maintenance/service incidents: name communication, escalation and rollback owners; establish approved notices and update expectations. Suspected security incident, data export/deletion, retention and backup obligations go to Security and qualified policy/legal reviewers. Do not supply invented notification deadlines, retention periods or a declaration of compliance. Preserve minimal metadata and never copy production customer conversation bodies into examples.

## 5. Exercise readiness and stop at the action boundary

Use synthetic cases before customer promises: outside-hours request, holiday/DST boundary, absent primary, burst arrivals, snooze/reopen, provider outage, renewal near notice cutoff, cancellation/access/export sequencing and suspected security incident. Record expected behavior, observed result, artifact, owner/date and gaps. A paper exercise validates only the procedure; actual tool routing, alerts and billing/access require separately authorized implementation and runtime proof.

Recommend BLOCKED for missing critical owner/calendar/terms evidence; REVISE for incompatible capacity or clocks; READY FOR OWNER REVIEW only when the stated scope has sufficient evidence. That state is not approval to sell, publish terms, configure renewal, send reminders, cancel/refund, delete data or activate alerts. Name the exact approval/action still required and preserve the reviewed worksheet version.

## Outputs and peer handoffs

Return the obligation register, coverage/clock matrix, supplied-input calculation, lifecycle owner matrix, exercise evidence and one readiness recommendation. For a tool choice include the existing mandatory comparison table; this guide does not waive it. Payments owns billing/entitlement implementation; Security owns data and incident-policy review; qualified legal reviewers resolve enforceable terms; operational incident/status/runbook owners resolve service execution. Confirm selected plugin availability before invoking optional specialists. No new skill or command is created.
