# Qualify updater trust and recovery

Use for O100. DERIVED procedure based on [updater](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/backend-and-desktop-tools/skills/tauri-stinger/references/research/desktop-capabilities-20261007/raw/updater-source.md) and [SQLite backup](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/backend-and-desktop-tools/skills/tauri-stinger/references/research/desktop-capabilities-20261007/raw/sqlite-backup-source.md). Refresh the exact plugin/CLI graph and use existing platform signing guides before a real release.

1. Collect installed versions, OS/architecture/package route, current trusted public key, update channel ownership, persisted schema versions and effect authorization. Identify code signatures, installer trust, updater payload signatures, TLS transport and feed policy as separate evidence rows.
2. Verify configuration embeds public key content, uses approved HTTPS endpoints and selects the intended target. Private key names/owners only belong in this record. Do not weaken transport or signature verification to bypass a failure. Artifact signature verifies the signed bytes; it does not by itself authenticate freshness, channel assignment, notes, destination policy or compatibility.
3. Bind final payload, signature content, source revision, target, version and delivery URL. Static metadata must include complete target records. Dynamic metadata uses the documented 200/update or 204/no-update contract. Validate release notes as untrusted display data and constrain accepted origins/redirect behavior using the actual client behavior.
4. Define monotonic version and channel policy, an intentional rollback exception, and how stale but valid signed payloads are rejected. The documented version-comparison override can allow rollback; that is a product trust decision, not a standard safe default. Do not enable it unless the owner accepts the exact recovery edge and Security reviews it.
5. Model existing clients trusting K1, bridge clients and future clients trusting K2. Before rotation, prove each installed version can obtain and verify the next artifact with its current key. A build trusting K2 does not make K1-only clients accept a K2-signed payload. Lost/compromised key paths need an explicit security and recovery decision; do not claim rotation automatically repairs previously installed clients.
6. Couple install/relaunch to a migration readiness contract. Define when backups occur, what partial installation means, and whether a previous binary can read post-update data. Test restored data and old/new binaries rather than declaring reinstall a rollback. Multiple package-manager and self-update owners require an explicit ownership contract.
7. Qualify valid update, tampered payload/signature, wrong target, unsupported schema, stale signed version, changed channel, wrong key, offline/proxy, interrupted download, disk-full, installer-start failure and relaunch/cancel behavior. Use an authorized isolated candidate environment. Tie each result to actual signed bytes and installed starting version.
8. Document staged rollout, rollback/recovery owner and communication without uploading or publishing in this procedure. Signing, key access, service writes, installation and live rollout require explicit authority. Security precedes Quality; absent native update proof stays OPEN.

The [synthetic cases](../examples/08-desktop-capability-decisions.md) distinguish policy review from native execution. No generic signing or downgrade guarantee is supplied.
