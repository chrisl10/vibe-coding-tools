# Qualify native acceptance beyond browser tests

Use for O104. DERIVED procedure grounded in test overview, WebDriver, shell and notification.

1. Inventory requirement -> native behavior -> target -> proof level before choosing a runner. Mark source/static, renderer mock, Rust logic, native IPC, packaged launch, installer/update and real-device results separately. A summed green count does not close missing target rows.
2. Reuse existing frontend and Rust tests for serialization, validation and state. Tauri mock runtime omits native webview libraries; browser mode launches no Tauri binary. They cannot prove OS permissions, actual command dispatch, vault access, process cleanup, package resources or platform integrations.
3. Select the real app driver route explicitly. Current Tauri docs distinguish embedded @wdio/tauri-service on Windows/Linux/macOS from direct tauri-driver on Windows/Linux. A macOS claim using direct tauri-driver needs another qualified route. Record service/provider/plugin versions and whether IPC mocking is enabled. Disable mocks for the native commands being accepted.
4. Any embedded automation server/backend access plugin is a privileged test surface. Bind access appropriately in the test environment and prove it is excluded or disabled in the intended production release. Do not ship a testing bridge merely because the E2E suite needs it.
5. Run actual allow/deny IPC cases against the selected window/origin and resolved permission union. Exercise invalid serialized input, path/scope denial, startup/shutdown, renderer reload and cancellation. A capability JSON validation checks shape, not runtime access or business authorization.
6. Test sidecar identity and framing with the final packaged binary; test persistence/migration with historical owned fixtures; test tray, shortcuts and notifications in the actual session. Bind the app/helper/resource hashes to each result. Real app acceptance requires real app execution, not a Python simulation of the expected decision.
7. Repeat relevant smoke checks on final delivery bytes and supported OS/architectures. Development launch does not prove installer paths/resources/quarantine or Windows installed notification identity. Mobile needs its approved native/device route and real platform permission behavior.
8. Record exact command, driver route, runner/device/OS, start version, app/package hashes, mock flags, logs, expected/actual outcome and unsupported row. Keep absent tools/platforms OPEN; no installation or paid provider is implied. Route CI topology to DevOps, formal boundary acceptance to Security, then final outcome review to Quality.

Use [the record](../templates/desktop-capability-evidence.md); this source package provides procedures and synthetic decisions, not a native acceptance run.
