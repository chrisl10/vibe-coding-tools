# Qualify Windows signing expectations

Use for O098. Read the dated digest. This is a DERIVED procedure; observed source cutoff is 2026-10-07.

1. Record Windows versions/architectures, installer type, delivery route, enterprise policy constraints, WebView2 assumptions, publisher identity and update mechanism.
2. Clarify terminology: a DV/OV/EV TLS or SSL certificate secures an endpoint, not a Windows executable. Choose a code-signing certificate or supported signing service with the identity owner. OV/EV refers to code-signing validation when discussing Authenticode. No purchasing or account creation is implied. Tauri.
3. Do not promise EV avoids SmartScreen. Microsoft states that EV no longer bypasses reputation checks; signed new binaries can warn. Record publisher/file reputation and the actual machine policy separately from signature validity. Do not promise a date or install count for reputation. Microsoft.
4. Do not copy Tauri's pre-June-2023 OV export recipe into a current certificate workflow. The identity owner must qualify current token, remote service, issuer or HSM requirements and supported signing integration. Tauri supports a custom sign-command route. Tauri.
5. Prepare only CI secret/identity REFERENCE names required by the approved service. Record protected environment, approver and timestamp policy. Never request certificate bytes or print token/password values. Release automation belongs to DevOps; identity acquisition belongs to the release owner.
6. Bind the exact EXE, installer, DLLs and sidecars to hashes. Inspect each expected signed item; installer signing alone does not establish every payload signature. Use installed tools on literal supplied paths, for example `Get-AuthenticodeSignature -LiteralPath 'C:\release\App.exe'` and `signtool verify /pa /all /v C:\release\App.exe`. Record signer, chain/status, timestamp, target OS and sanitized result. Tool absence is OPEN, not permission to install.
7. Test the final downloaded installer in representative clean supported Windows environments with the intended browser/download route, enterprise policy and SmartScreen or Smart App Control state. Record prompts and blocked launch explicitly. Signature PASS with reputation warning is two separate findings; never instruct users to weaken policy as a release acceptance step. Microsoft.
8. Test install, launch, sidecar behavior, update, interrupted install and uninstall. Define supported recovery and persistence compatibility before considering older-version reinstall. Fill [the template](../templates/native-release-qualification.md); updater signatures remain a different trust layer. Tauri updater.

Microsoft's consumer reputation guidance does not provide manual reputation review as a universal fix; enterprise review routes differ. Keep submission and any external upload closed absent explicit approval. Microsoft.
