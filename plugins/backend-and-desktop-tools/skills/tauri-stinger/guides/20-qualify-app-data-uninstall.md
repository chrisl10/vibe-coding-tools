# Qualify app-data cleanup and uninstall

DERIVED O105 procedure grounded in the digest. An app-created export in Documents remains user-owned. Creation by the app does not by itself grant future deletion authority.

1. Separate removal of installed application binaries, removal of proven app-owned private state/caches, revocation of scoped access, and retention of user documents/exports/backups. Record exact package route and OS target. Installer defaults, path patterns, age/mtime, filename extensions and empty directories are insufficient ownership evidence.
2. Inventory an app-owned provenance manifest with application identity, installation/data generation, exact resource identifier, ownership class, creation action, supported native identity/hash evidence and retention/recovery policy. Validate the manifest against trusted app state; imported manifests and renderer paths cannot authorize deletion. A hash proves bytes, not ownership. Migrated/legacy files of unknown ownership stay retained and OPEN.
3. Prepare a dry-run removal manifest naming the exact permitted app-owned candidates and excluded user files, symlink/reparse/hardlink aliases, shared stores, credential entries and externally synced data. Normalize components and bind candidates to qualified handles/identities. Do not traverse into an external directory through a link. Do not recursively delete a directory whose descendants include unowned/unknown files.
4. Obtain explicit user approval for the specific removal plan and recovery limitations before a real cleanup. Installation or upgrade approval does not grant uninstall or data deletion. Preserve all user documents and original import sources; any separate requested document deletion needs its own exact approval and ownership determination outside this default cleanup procedure.
5. Quiesce app writers, sidecars and background jobs; coordinate multiple instances and the installer. Revalidate identity at the actual deletion boundary using qualified OS primitives, then remove only verified candidates. A read-before-delete path check alone is vulnerable to TOCTOU. On mismatch or unsupported primitive, retain and report. General Rust/OS implementation returns to its owner.
6. Define recovery before deletion: an authorized protected quarantine/backup with exact restore behavior or an explicit irreversible deletion decision. Moving files is itself a mutation requiring approval. Quarantine/backup may still contain private data and need access/retention review. Partial failure leaves a per-item result ledger and retains uncertain items; do not retry a broad wildcard cleanup.
7. Review the actual installer script and uninstall hooks. MSI supports wildcard removal and install/remove modes, so inspect each rule rather than infer that only app files are removed. MSI. Apple's app-removal guidance preserves documents and distinguishes optional uninstallers. Apple. These sources do not prove NSIS, AppImage, Linux package-manager or a consumer's custom uninstall behavior.
8. Verify only on explicitly authorized disposable app-owned targets with final package hashes: install, generated app state, user document/export sentinel, uninstall, reinstall and recovery. Record retained sentinels, removed exact owned items and failure behavior. OS uninstall, cloud sync/backup, credential vault revocation, provider deletion and mobile storage remain OPEN until their owners supply evidence and separate authority.
