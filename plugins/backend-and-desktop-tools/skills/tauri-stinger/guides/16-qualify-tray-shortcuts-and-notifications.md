# Qualify tray, shortcuts and notifications

Use for O102. DERIVED procedure grounded in tray, shortcuts, notifications and capabilities.

1. Name the user action and supported OS/version/desktop-session matrix first. Choose tray quick actions, foreground accelerator or global shortcut deliberately; global registration affects other applications. Record hide/close/quit semantics and do not silently leave a process running after the user expects quit.
2. Review tray-icon feature, plugin initialization and selected capabilities. Rust-owned integration may avoid frontend plugin grants; application commands still need authorization. Restrict creation, mutation and registration to the expected local window. Compare effective permission unions.
3. Separate tray menu handling from raw icon mouse events. Tauri's documented Linux tray mouse events are unsupported even though a visible icon/context menu can work. Provide an ordinary in-app route for required actions and test the declared desktop/session. Do not make essential exit/recovery depend on a Linux double-click event.
4. Define shortcut collision, disabled preference, layout/modifier differences, Pressed versus Released, repeated key events and lifetime ownership. Treat registration failure as a recoverable error, never a pass. Unregister only owned shortcuts on reconfiguration/exit and avoid duplicate callbacks after renderer reload. Test when the app has and lacks focus; registration success is not proof of triggered behavior.
5. Check actual OS notification authorization, then prompt only at a user-relevant point. Denial/revocation leaves an in-app outcome; never repeatedly prompt or assume a permission grant causes delivery. Keep private message text and credentials out of lock-screen notifications unless the user explicitly chooses visibility.
6. Distinguish Windows installed app identity from development PowerShell identity. Inspect final installed application notifications. Notification interactive actions are documented mobile-only; do not promise the same desktop buttons or behavior. OS focus/quiet modes can affect observations; capture actual state without changing user settings.
7. Test menu show/focus/restore, shortcut conflicts and repeat/reload cleanup, denied/revoked notifications, foreground/background, suspend/resume, quit and restart. Record target/session/app hash, expected/observed behavior and accessible fallback. Native sends and OS configuration changes are separately authorized.
8. Write [the record](../templates/desktop-capability-evidence.md). UI mocks establish event handling only. Missing real OS behavior remains OPEN, even when compilation and permission schema checks pass.
