# Qualify local data migrations and recovery

Use for O096. DERIVED procedure grounded in SQL, Store, Stronghold, SQLite transactions WAL and backup.

1. Inventory each file/database/vault: location, owner, sensitivity, user identifiers, app identifier changes, backup/export/deletion policy and supported old/current versions. Ordinary Store/SQLite persistence is not an encryption claim. Separate schema design (DB owner), Rust database implementation (Rust owner) and Tauri integration (this pair).
2. Declare supported upgrade edges, schema versions and old-reader compatibility. Inspect historical migration bytes/checksums and database identity. Never rewrite an applied migration or guess a backfill. Unknown values remain unknown until the owner supplies a policy.
3. Use unique, ordered SQL migration versions in the existing mechanism. Tauri SQL documentation describes transaction rollback for migrations; inspect the resolved plugin implementation and test the chosen engine. Do not expand atomicity to Store files, vault changes, downloads or external calls.
4. Decide when preload/load runs migrations and keep ordinary UI access closed until readiness is established. Define a single migration owner across windows and app instances; SQLite has one concurrent writer, not unlimited concurrent mutation. Handle busy/timeouts and interrupted startup explicitly; do not add a generic retry loop around non-idempotent work.
5. Produce an application-consistent backup before a destructive transition. For SQLite use the established backup API or a qualified maintenance/quiescence procedure covering WAL and related files. Copying only the live .db may miss committed WAL state. Record destination security, backup hash, validation, retention and restore owner without exposing content.
6. Test first run, every supported historical schema, repeated launch, interrupted transition, invalid/corrupt state, failed SQL, concurrent writer/instance, full disk and locked vault. Keep original data untouched when detection fails. Report recovery guidance; never auto-delete a database to make startup work.
7. Choose forward repair, restore from proven backup or compatible reinstall. An older binary can be cryptographically authentic and still unable to read the new schema. Do not call a Down migration safe rollback without row/content and old-reader tests. Preserve unknown compatibility as a blocking recovery finding.
8. Verify explicit save/flush lifecycle for crash-critical state; graceful exit or debounce does not establish hard-crash durability. Test storage permissions, OS backup, reinstall/app-identifier relocation and user-requested export/deletion on each supported platform.
9. Use the [SQLite exercise](../examples/09-sqlite-recovery-exercise.py) only to teach transaction/backup mechanics in an owned temporary database. It does not use Tauri SQL or qualify an app's migrations. Record real application proof in [the evidence record](../templates/desktop-capability-evidence.md).
