# Build and qualify a Go desktop application

DERIVED procedure grounded in [CLI](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/backend-and-desktop-tools/skills/go-desktop-stinger/references/research/raw/wails-cli-source.md), [build](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/backend-and-desktop-tools/skills/go-desktop-stinger/references/research/raw/wails-build-source.md), [embed](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/backend-and-desktop-tools/skills/go-desktop-stinger/references/research/raw/go-embed-source.md) and [requirements](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/backend-and-desktop-tools/skills/go-desktop-stinger/references/research/raw/wails-setup-source.md).

1. Freeze source revision, module and frontend lock graphs, actual installed CLI/Go versions, flags, OS/architecture, package route and permitted commands. Inspect tooling before requesting installs. Generated bindings, remote templates, npm hooks and Go toolchain/module downloads are effects to account for.
2. On an authorized equipped consumer target, run its existing Go format/vet/unit/contract checks and frontend checks. Use race detection only on supported toolchains/targets; record unsupported rows. Regenerate bindings if required and compare method/DTO inventory. These checks do not prove the native WebView.
3. Produce the frontend build with the approved command. Inspect embedded assets, source maps, dotfiles admitted by all: patterns, public config and secret canaries. Confirm correct index/assets and runtime routes; never assume dev-server behavior matches embedded production output. The source records a dynamic-asset/Vite compatibility warning requiring actual graph verification.
4. When authorized, run the installed compatible `wails build` using reviewed target/flags. It produces build/bin artifacts. CLI platform flags do not prove cross-compilation/native prerequisites or target runtime support. Optional NSIS or WebView2 installer strategies need release-owner decisions; no installer/tool download is automatic.
5. Run the actual native app on each supported OS/architecture and exercise the first user journey, generated bridge success/refusal, origin/navigation denial, dialog cancel, worker cancellation, close/quit, offline and persisted restart. Browser mocks are separate evidence. Record command, OS/runtime versions, output and exact binary SHA-256. Absent targets stay NOT_RUN/OPEN.
6. When distribution is authorized, review final artifact identity, nested dependencies/resources, install/uninstall hooks, signatures/notarization and runtime prerequisite delivery with release peers. Verify install/launch/restart/recovery/uninstall only on approved disposable targets, with retained user-document sentinels. A build result is neither signed distribution nor automatic updater support. Store publication, signing credentials, upload and live release stay separate approvals.
7. Write the consumer library report and [evidence worksheet](../templates/desktop-app-evidence.md): achieved acceptance, exact tests/artifacts, error/failure results, source snapshot, supported target rows, data recovery and unresolved owner gaps. Run independent Security, resolve medium-or-higher findings, rerun affected checks, then Quality. Parent loads repository health and obtains user review/commit-push approval before those actions.
