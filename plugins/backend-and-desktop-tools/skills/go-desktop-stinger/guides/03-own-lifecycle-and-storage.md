# Own application work and app-local state

DERIVED procedure using runtime readiness, hooks, Go context and OS storage.

1. Allocate service state in startup, record BOOTING/READY/FAILED and preserve startup errors without assuming a hook error return. Defer runtime UI calls until the qualified OnDomReady path. Reject bridge work before READY or after STOPPING. Inspect actual callback signatures; source prose conflicts are recorded in the digest.
2. Give every long operation a unique bounded ID, context/deadline, cancellation function, completion signal and single state owner. Define queue and output limits, timeouts, duplicate IDs, retry/idempotency and partially visible results. Avoid locks across blocking UI/runtime calls. Wails app context is not an automatically cancellable per-request operation.
3. Cancel jobs through a narrow method that checks job ownership; cancellation signals work but does not join it. Bound shutdown waits, coordinate worker completion and close resources once. OnShutdown occurs after frontend destruction, so cleanup must not depend on a new UI event/dialog. OnBeforeClose policy must not conceal irreversible effects or silently replay work. Forced process exit cannot be represented as a guaranteed graceful callback.
4. Remove frontend event listeners on teardown/reload and correlate progress/terminal events. A disappearing UI must not create duplicate jobs, unbounded retained output or orphaned goroutines. Provider work remains behind an approved contract with separate live-traffic authority.
5. Separate settings, structured user content, caches, secrets and ephemeral handles. Use an app-specific directory under a verified OS location and classify retention/permissions. UserConfigDir is a location helper, not encryption or ownership approval. Schema/retention decisions remain with the data owner; this specialist integrates the accepted contract.
6. Specify versioned migrations, single/multi-instance locking, transactional/atomic updates, backup/restore and old-reader compatibility before durability claims. Temporary-write, sync and rename need checked errors and exact OS/filesystem behavior. A single File.Sync success is not proof of crash-safe directory publication; generic rename guarantees must not be assumed across targets.
7. Keep user-selected sources and exported documents distinct from app-private state. Parse import content as bounded data; export requires exact destination/overwrite policy and qualified publication. App uninstall never deletes user documents by pattern, mtime or creation assumption. Secret store, cloud backup and provider deletion need their own owners/approvals.
8. Test readiness races, cancellation before/during work, reload, repeated close, blocked worker, partial write, migration failure, concurrent instances and recovery with approved disposable fixtures. Native file races and crash durability remain OPEN until real target proof.
