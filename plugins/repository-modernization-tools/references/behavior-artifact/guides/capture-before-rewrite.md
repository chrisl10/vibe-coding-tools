# Capture observable behavior before a risky rewrite

Read [the dated digest](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/packs/repository-modernization-tools/references/behavior-artifact/references/research/behavior-artifact/distillation.md) and use [the worksheet](../references/behavior-artifact-worksheet.md). ApprovalTests supplies snapshot comparison; Pact supplies interaction verification. This guide adds source and authority controls to those methods.

1. Pin the actual baseline commit, working tree delta hashes, runner/version, operating system, dependency lock hash, fixtures, invocation and environment variable names. Never store secrets, private messages or customer data in snapshots. Use authorized sanitized fixtures and record transformations.
2. Select the boundary callers depend on: return values, status and headers, error type, ordering, data writes, emitted events and retries. Label coverage omitted. Freeze or inject a clock, randomness and external adapters only in owned test fixtures; record that substitution. Do not claim a fake network, filesystem or provider exercise proves production effects.
3. Execute before changing the implementation. Retain exit code, stdout/stderr with redaction, result hash and side effect record. Record current quirks and undesirable outputs as OBSERVED_CURRENT. Record intended acceptance separately as INTENDED_REQUIREMENT with the approved source. A bug in the baseline is not a silently approved permanent requirement.
4. Name nondeterministic fields. Any normalization must have a written reason, exact transformation and retained safe unnormalized evidence where permitted. Do not strip IDs, times or ordering when they carry business meaning. If runs differ without an explained cause, mark the case UNSTABLE and stop claiming a golden baseline.
5. Compare the candidate at an equally pinned revision using the same inputs and runner. Classify each difference as unintended regression, authorized behavior change or unresolved. Never auto-approve received snapshots or rewrite expected outputs simply to pass.
6. For contracts, identify consumer/provider revisions, states and matching rules. Record consumer execution separately from actual provider verification. Schema validation, mocked consumer success and screenshots do not prove provider compatibility.
7. Hand the evidence to the existing refactor-safely command or the assigned implementation owner. Verification may exercise an owned isolated fixture; this guide does not grant a rewrite, migration, live request, install or side effect. Run the existing Security, Quality and parent Repository Health gates for source changes before any separately authorized commit.
