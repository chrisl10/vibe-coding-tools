# Run bounded remediation through existing owners

Read [dated source digest](distillation.md), then fill [worksheet](remediation-worksheet.md). This pack composes commands. Code Bloat reports read-only findings, Remediation Planning supplies its approved planning process, and the selected language/framework/data/UI owner implements only the authorized change. No Scoped Refactor skill, agent or helper is assumed.

1. Pin actual repository revision and dirty bytes, current approvals, ownership and test budget. Record baseline observable behavior before implementation. Existing failures remain visible.
2. For each dead-code candidate, inspect actual dynamic/string dispatch, reflection/name registries, generated entries, package exports, framework discovery, optional/platform paths, scripts, CI and downstream consumers. Read hits, not just counts. A graph gap or a computed reference yields Unknown or Live. Before deletion, require current specific action/path authorization and a recovery plan covering actual bytes. Consult [Knip limitations](raw/knip.html) and [computed import behavior](raw/mdn-import.html).
3. For each duplication candidate, read both responsibilities and change history. Explain why they are the same evolving concept. Preserve intentional differences. Reject an extraction justified only by syntax or clone percentage. This is a review policy, not an instruction to force all duplication into shared code.
4. For a giant service, record dependencies, state, transactions, authorization and failure paths. Propose one seam within the current process first. Preserve accepted behavior and transaction ownership. Separate any microservice/deployment proposal from this batch. Compare against [observable-behavior definition](raw/refactoring.html).
5. For incremental modernization, specify one capability, routing seam, compatibility conditions, state/reconciliation owner, rollback trigger and evidence. The [strangler discussion](raw/strangler.html) supports incremental preparation, not an automatic traffic switch. Obtain specific authorization before cutover, retirement, provider/settings change or migration.
6. Rank technical debt from dated known customer impact, change frequency, incident/security evidence, operating cost and reversibility. Keep unavailable evidence unknown and illustrative numbers labelled. Recommend one ordered batch with rationale rather than claiming measured savings.
7. Before vendor-fork maintenance, identify upstream URL/revision, imported-byte hashes, license/notices, local patches, supported contracts and maintenance owner. Inspect any proposed upstream comparison while preserving local patches and attribution. [Git submodule mechanics](raw/git-submodule.html) do not supply update authority or license compatibility. No force update or blanket replacement is included.
8. Run only existing authorized relevant baseline/candidate checks under comparable recorded conditions. Bind results to exact revisions or dirty-tree hashes. Missing proof blocks equivalence. A rollback proposal never authorizes resetting another worker's files.
9. Deliver exact diff and worksheets, observed results and missing proof. Close the final candidate through Security, independent Quality after clearance and orchestrator Repository Health. Commit, push, release, provider writes and publication retain their distinct approval gates.

[Constructed negative cases](negative-cases.md) are NOT_RUN. This source procedure is not proof that an application was remediated.
