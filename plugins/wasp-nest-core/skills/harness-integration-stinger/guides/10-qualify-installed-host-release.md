# Qualify release claims against installed-host receipts

Use for O300. The [claim digest](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/src/skills/harness-integration-stinger/references/research/availability-proof/distilled-availability.md) supplies primary-source boundaries. Reuse [the host receipt matrix](../templates/installed-host-release-matrix.md); packaging and release-CI implementation belong to `ci-release-stinger`.

1. Pin the exact candidate: source commit or source manifest hash, built owner version, artifact hash and retained resources. Record what structural/build checks actually passed. Such checks qualify source/package content only.
2. For each Claude Code, Cursor, Codex and Cowork target, record carrier, host version, install/selection observation, exact owner and prerequisites, native discovery and supported invocation path. Use [selected-availability proof](08-prove-selected-availability.md). Every absent observation stays UNEXECUTED or UNKNOWN; no blanket all-host claim from one build.
3. Under separately authorized installation and execution, choose a bounded local fixture that demonstrates reading the real skill/resources, command routing and, if claimed, actual agent discovery/dispatch, hooks or MCP behavior. Record request, actual tool/role identity, result, failures and side-effect boundary. Synthetic resolver tests are a separate row. A native slash-command selector screenshot establishes discovery only, not successful routing or invocation.
4. Keep account-scoped tests separate. A plugin can load while a connector is disconnected or denied. Never claim working external integrations without their own observed access and authorized operation. Do not borrow a signed-in account or read credentials to manufacture proof.
5. Attach classified degradation for each unsupported surface: preserve, translate, degrade or drop with the retained user outcome and loss. For a direct skill-read fallback, say native command/agent loading was not exercised. Hook behavior requires actual configured event execution; fail-open observational behavior does not prove an authorization gate.
6. Bind independent Security then Quality and repository-health evidence to the final candidate. A changed payload invalidates its old candidate proof; inspect affected tests and rerun the necessary gates. Do not reuse a stale success across rebuilt resources or role/config changes.
7. Draft claims per host and surface only. Approved example: “Source package validation passed; Codex native role activation is unexecuted.” An “all four hosts supported and working” claim requires four populated observed execution rows plus their applicable resource, prerequisite and access receipts.

This guide and source exercises perform no real installation, registry/config change, release, account write or publication. See [release counterexamples](../references/examples/availability-proof/O300-release-claims.md).
