# Coordinate parallel workers with exclusive ownership

Use this guide when an authorized task needs several independent workers. Harness Integration owns capability selection and the coordination procedure. AppPrimer Zero owns the reusable wave schema, validator and assignment templates. Read the [research digest](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/src/skills/harness-integration-stinger/references/research/worker-coordination/distilled-worker-coordination.md) and [worked cases](../references/examples/worker-coordination/README.md).

## 1. Prove the dispatch surface

Read the current host's actual tools and policies. Resolve each specialist from the selected plugin registry and its prerequisite owner. A cached agent file is not an enabled native role. For source-checkout forge work, record the source owner separately from installed selection. Record actual dispatch, status, steering and stop tools without inventing API names. A capability documented for another product/version is insufficient.

Claude Code and Cursor document subagent mechanisms; OpenAI documents subagent configuration and inherited permission behavior. Those documents are background evidence, not proof that this session exposes their tools. Cowork receives this procedural skill; parallel dispatch remains unqualified until the session exposes and verifies a suitable native surface. If dispatch, capacity or supervision is unknown, stop parallel execution. Continue only authorized serial preparation and disclose loss of independent execution/review.

## 2. Establish the actual budget and shared boundaries

Read the live limit and its counting convention. Count the coordinator once, every active implementer or reviewer, and any nested workers. An upper limit in config is not a count of free slots. Do not infer capacity from a completed old wave or test by creating excess workers. Honor role and model inheritance; do not override model, effort, sandbox or permissions without applicable user authorization. Effective settings can be unknown even when inheritance was requested.

Inspect the real checkout and existing dirty owners. Give each worker canonical disjoint file prefixes or exact paths. Assign shared configuration, package/lockfiles, DTOs, schema/migrations and cross-cutting tests to named single owners. Prefix disjointness alone misses symlinks and semantic coupling: inspect those boundaries. Worktree isolation, when already authorized, isolates files but does not settle shared interfaces. A worker requests changes from the shared owner; it does not overwrite another lease.

## 3. Reuse the existing handoff gate

From the trusted selected Core root, run `hooks/resolve-component.py harness-integration-stinger --workflow worker-coordination` through the available Python runtime. This explicit workflow key requires App Primer selection before the dependent handoff step. Source-checkout construction may inspect canonical artifacts, but does not claim an installed selection.

Locate selected `app-primer-zero-stinger`, verify its owner/prerequisites and load `references/capacity-and-review.md`, `templates/worker-brief.md`, `templates/wave-handoff.md` and `scripts/validate_handoff.py` relative to the resolved skill root. In this source repository its path is `packs/app-primer-zero/skills/app-primer-zero-stinger`. Do not assume that path exists in a Core-only installed carrier. If absent, prepare the record and report the missing prerequisite; do not install it or copy an archived validator into production.

Run the existing helper on the bounded wave JSON. Keep its entire limitations list with the verdict. A Draft contract may be structurally valid preparation; dependent ready implementation remains blocked. Validate exact accepted revision pins, then inspect the approval evidence rather than accepting strings as authorization. Preparation PASS does not launch workers, certify capacity or approve an action.

## 4. Delegate and inspect outputs

Pass the bounded AppPrimer worker brief, original user scope, inherited deadline, owned paths, excluded shared files, expected checks and retry limits. Tell workers that others are active and they must preserve their work. Keep nested work disallowed unless explicitly scoped, counted and supported. Record successful dispatch and returned identity; submission is not completion.

Review actual changed files or check output at least every ten minutes and track substantive progress every five minutes under the operating policy. A progress claim does not reset a stall clock. Preserve earlier failed attempts when reassigning work. On a ten-minute stall, stop the worker through the available native surface, inspect the acknowledgment and its final status, then redistribute only the remaining authorized scope. If stop is unavailable or uncertain, do not start a replacement writing the same paths. Surface the blocker and preserve the lease. No timer or watchdog is implied by these instructions.

## 5. Stop, hand off and qualify the combined candidate

At a deadline or owner stop, request worker stop, inspect final status and any owned background processes that the host exposes, and save coherent artifacts. Use the six-field report from the operating policy. Release ownership only after the earlier worker cannot continue writing. A stopped worker's partial output remains partial until inspected and integrated.

Integrate under applicable authority and pin the exact final combined SHA or source manifest. Run consumer/integration checks on that candidate, then independent Security, Quality and repository-health review in order. Changed source after Security invalidates its candidate binding; changes after Quality require renewed applicable gates. A worker's green shard, structural PASS or idle flag does not prove the combined application. Keep [the coordination record](../templates/worker-coordination-record.md) with preparation, selected capabilities, observed execution and final integration proof clearly separated.
