# 13. Qualify webhook forgery, replay and recovery

O156. Use [webhook trust worksheet](../templates/security-design/webhook-trust.md). For Stripe processing and entitlements, resolve the selected Platform and Release owner and load [Payments guide 11](https://github.com/legioncodeinc/vibe-coding-tools/blob/main/plugins/platform-and-release-tools/skills/payments-stinger/guides/11-enforce-server-entitlements.md). Schema/transactions belong to DB; another provider needs its actual signature/retry contract. This procedure introduces no generic webhook engine.

1. Identify sender, endpoint, environment, event/object mapping, secret/key provenance, signature algorithm and SDK revision. Do not request or print key values. Capture names and approved configuration provenance only. CLI and Dashboard Stripe endpoint secrets differ.
2. Preserve original body before parsing; impose framework/platform-appropriate body bounds and verify signature with the supported provider SDK before acceptance or effects. Exercise missing/bad header, changed bytes, wrong environment/key and timestamp outside the actual configured tolerance. A tolerance of zero in Stripe disables its recency check; do not use that to make replay tests green. Unknown provider timestamp semantics remain unknown.
3. Distinguish valid delivery from completed processing. Persist a durable inbox/queue acceptance or atomically commit the authorized projection before acknowledging success. A unique event insert alone is not completed work; an in-memory callback after 2xx can disappear. Define pending, leased, failed and completed recovery semantics with the existing DB/Payments owners.
4. Test two concurrent deliveries, worker crash before/after effect, duplicate event IDs, distinct IDs for one business action, out-of-order events, persistence failure and queue failure. Use object-level business invariants and recoverable work, not a promise of exactly-once delivery. Current-state reconciliation must use the same serialized writer and authorized tenant/object mapping.
5. Keep dedupe/effect history during approved recovery. Never clear dedupe rows as a generic replay procedure. Re-fetch or recover persisted verified work through an authorized operator path; do not disable signatures to accept an expired recorded delivery. Log sanitized event metadata and operation status, not payloads or keys.
6. Plan endpoint-key rotation overlap per provider contract, stale key refusal after retirement, incomplete delivery recovery, complete pagination for reconciliation and expected retry behavior. Provider/credential changes require explicit owner authorization. Record actual evidence, or label the packet source-only.
