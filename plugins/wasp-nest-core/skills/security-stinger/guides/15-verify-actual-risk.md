# 15. Select verification from actual risk

O164. Use [risk coverage worksheet](../templates/security-design/risk-verification.md). Sources: [threat model](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/src/skills/security-stinger/references/research/security-design/raw/owasp-threat.md), [authorization](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/src/skills/security-stinger/references/research/security-design/raw/owasp-authorization.md), [ASVS overview](https://github.com/legioncodeinc/the-wasp-nest-source/blob/main/src/skills/security-stinger/references/research/security-design/raw/owasp-asvs.md). Use a pinned ASVS version and exact requirement only after loading that version's requirement text; this overview capture does not supply every requirement.

1. Pin the candidate source/artifact, target environment, supplied authorization and scope. Enumerate the material threats and changed paths from guide 11, including immediate trust/permission neighbors. Baseline passing tests carry forward only where the relevant artifact/behavior did not change.
2. Map each threat to a testable invariant, actor/fixture, request or operation, expected denial/allow result, independent side-effect check and evidence collector. Include positive allowed controls plus forged/revoked/cross-tenant actors. Choose integration/runtime proof when the invariant depends on framework execution, database roles, pool reuse, provider signatures or published artifacts.
3. Choose techniques for that invariant: source review, dependency/provenance analysis, unit boundary exercise, representative integration test, browser/runtime test or authorized provider verification. Reuse the selected Harness owner's capacity/ownership procedure and existing app tests; create no duplicate scanner. Tool output is evidence within its scope, not a security verdict.
4. Record exact command/fixture, revision, artifact hashes, actual results, sanitized logs and remaining gaps. Distinguish NOT RUN, SOURCE REVIEW, SYNTHETIC EXERCISE, TARGET RUNTIME PASS and TARGET RUNTIME FAIL. Expected results in a worksheet are not observed results.
5. A blank coverage row or unavailable target is unproven. Severity acceptance names the human decision and scope; green unit tests do not waive an untested tenant/export or webhook effect path. After relevant corrections, re-evaluate the actual candidate and any neighboring invariants affected, per the existing audit procedure.
6. Formal audit clearance remains Security then Quality then parent Repository Health on the final candidate. The author of this source packet does not independently approve it. No target supplied in this update means source qualification only, never a blanket application pass.
