# Traffic capacity routing guide
Plugin owner: platform-and-release-tools. Required: Core and selected platform owner. Outcome O173.

## Domain and triggers
Measured traffic spikes, concurrency/DB/pool/queue bottlenecks, capacity/SLO/cost, admission and recovery planning. Staffing hire/services capacity remains business-and-product-tools Capacity Planning.

## Inputs and outputs
Inputs: actual service/journey/environment/revision, UTC aggregate traffic/latency/CPU/memory/DB/queue/downstream observations with sampling evidence, adopted SLO/budget, dated provider constraints and owner decisions. Missing inputs remain explicit gaps.
Outputs: completed measurement worksheet, cited bottleneck hypothesis, unit-checked scenario math, SLO/cost exposure, proposed admission/recovery and future bounded validation acceptance. No target/native/customer/performance claim from source examples.

## Dispatch and boundaries
For source work read root catalog. For installed work resolve traffic-capacity-stinger through trusted Core selected-plugin resolver and obey [arming contract](../SKILL.md#dispatch-and-arming-contract). Cached presence is not selection. Read the returned skill path before work; preserve host/tool availability, scope, clock and file ownership. Direct skill fallback needs the user's allowed approach and honest carrier reporting.

Runtime is read-only advisory. No load/probe, distributed benchmark, new tool, settings/provision/autoscaler change, paid resource, credential or provider write. Actual owner-accepted target/rate/budget/stop scope is required before a separately routed test. Sentry owns telemetry, Vercel/DevOps platform execution, Operating Cost billing model, DB pool/query changes and Security privacy/tenant/abuse decisions. Resolve optional owners before dependent stages. Reports and file writes follow actual carrier read-only capability.
