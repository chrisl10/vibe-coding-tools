# Explain one repository journey for a beginner

Create a source-linked tour that lets a new coder locate the entry point and understand one request's path through the repository.

1. Confirm the target repository/revision, authorized read scope, one reader goal and the supported output path under the target Knowledge domain. Keep the existing Knowledge format and Library lifecycle. Ask before expanding to an entire codebase or changing source.
2. Read actual README, manifests and route/CLI entrypoints within scope. Select one concrete behavior with a visible caller, work and response. Follow imports and calls only as needed for that journey. List unavailable files or dynamic dispatch as gaps.
3. Build the tour ledger from actual files: revision/hash, file/symbol/line, role in the journey, observed condition, related requirement/contract status and missing evidence. Distinguish files read, tests declared and checks actually executed. A function's name does not prove its implementation or permission policy.
4. Read accepted contracts and ADRs separately from Draft PRDs. If source conflicts with a contract, describe both with a concrete locator and leave the discrepancy visible. A future requirement never becomes a current feature merely because the tour includes it.
5. Resolve optional `technical-explainer-wasp-drone` and `technical-explainer-stinger` through Core's selected-plugin registry for bounded novice wording, glossary, one analogy and teach-back, when available and selected. Pass the verified journey ledger and source scope. When absent, Knowledge still writes the source-grounded tour; mark the optional learning review unperformed rather than inventing a substitute agent or native dispatch.
6. Write an Explanation with one reader outcome first: what the journey does, which real files to open and why each matters, then who may request what, the visible branches and the missing implementation/runtime evidence. Keep instructions for executing software out of this explanation unless a separate authorized how-to is requested.
7. Reuse Technical Explainer's fidelity criteria: actor, action, object, permission, conditions, order, result, status and uncertainty. Place the exact factual account alongside any analogy. Preserve private paths and source details only in the authorized internal audience.
8. Review the rendered tour against each ledger row. Ask one teach-back question about a meaningful boundary, such as whether sign-in alone proves access to another workspace. Keep reader understanding pending until the reader responds. Source-link checks establish traceability, not comprehension or security correctness.

Grounding: update digest. The local digest and dated capture ledger preserve the update provenance.
