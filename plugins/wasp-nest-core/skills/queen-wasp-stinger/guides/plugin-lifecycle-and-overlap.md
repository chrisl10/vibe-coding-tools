# Qualify a distribution, stage an upgrade and resolve overlapping skills

Use this guide for O210 and O297. Load the research digest. Start with the [upgrade record](../references/templates/plugins/upgrade-record.md) and [overlap worksheet](../references/templates/plugins/overlap-decision.md). Construction stays with Queen; actual selected-host behavior belongs to Harness Integration. Supply-chain disposition belongs to Dependency Audit.

## Pin the existing capability before proposing a change

Read the catalog and the current owner's canonical skill, agent, commands and negative routing triggers. Record the user's requested outcome and the expected deliverable. Compare at least the closest existing owner and any pack prerequisite. Use the existing outcome discovery helper to find candidates, then inspect their scope. It is a lexical discovery aid, not a semantic duplication verdict. The topology checker enforces one name/owner, but differently named components may still compete for the same work. Implementation evidence

Evaluate the outcome, input evidence, output contract, authority boundary, runtime dependencies, supported host and acceptance checks. An explainer and an implementer may use the same technical terms yet have different deliverables. A generic audit and a framework-specific audit may coexist if their ownership boundaries and handoff are explicit. Two pairs promising the same deliverable from the same trigger need a decision before another pair is forged. Prefer reusing or enhancing the current owner when it can satisfy the outcome. Write the limitation when a new owner has a distinct job. Do not merge or delete inherited components as an automatic deduplication step. Topology and pairing evidence

## Stage a reviewable upgrade

1. Record the prior source revision or content manifest, candidate source manifest, generated plugin identity/version, client version and selected prerequisite closure. For uncommitted source, the Git ancestor alone cannot identify the candidate. Hash the relevant content. Repository VERSION drives generated manifests; internal skill dates do not. Builder evidence
2. Review the actual delta in skill/agent/command behavior, hook execution, permissions, MCP or network use, dependencies, licenses and owner placement. Name any changed side effect. Preserve the previous qualified artifact and its evidence. Do not copy credentials or private user content into an upgrade packet.
3. Validate canonical source and owner prerequisites with the existing tools. Build into a new task-owned output directory. Use `/qualify-wiring` to compose the existing validation and projection checks. Compare the actual generated manifest, command adapter, role and prerequisite paths. Check archive integrity and the published payload's own hash where publication is separately authorized. Existing gates
4. Record independent Security, then Quality, then direct orchestrator Repository Health against the same frozen candidate. A correction invalidates affected prior evidence. Preserve old results as historical records and bind the final acceptance to corrected bytes.
5. Present the concrete candidate and remaining installed-host checks. Installation, registry/settings edits, trust changes, publication, push or automatic updates are separate actions requiring authorization for the current task. A source-building request does not perform them.

The receipt must distinguish source validation, generated projection, archive integrity, selected installation, loaded session and actual invocation. Claude documents listing refresh separately from installed updates and keeps running-session versions until reload; Cursor's version field does not establish the same timing. Do not write one universal upgrade command for every client. Official host evidence

## Verify an authorized installed upgrade

After specific authorization, hand the exact package/version/hash, scope and approved actions to Harness Integration. Record the actual selected owner/prerequisites and client inventory before and after. Use a bounded, non-destructive invocation with task-owned input and explicit expected output. If the host cannot prove which revision it loaded, report package presence and invocation coverage separately. No screenshots or screenshots of slash-menu labels prove source-byte identity by themselves.

Keep the prior package and restore instructions as preparation. Do not promise atomic rollback unless the actual host supports it and its result was checked. Restoring instructions does not undo a sent message, changed provider setting or database operation. Report those effects separately; do not execute them merely to test the upgrade.

## Resolve a collision without silently replacing an owner

Use the overlap worksheet to write one recommendation: reuse, enhance, compose existing owners, or forge a distinct owner. Include trigger examples that should route to each owner and negative examples that must not. A command may orchestrate several owners; that is not a reason to invent an all-purpose specialist with the same responsibilities. Record a disputed owner or accepted interface change before editing dependent work. Required Core foundations retain their current placement. Registration changes source dispatch; it does not prove installed availability. Catalog snapshot

Acceptance means the outcome has an explicit owner, a differentiated scope and matching source/projection evidence. Unavailable native execution stays unverified. The illustrative cases cover these decisions without claiming a real upgrade was run.
