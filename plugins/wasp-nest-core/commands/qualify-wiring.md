# /qualify-wiring

## Mandatory process

1. Load `pest-controller-suit` first. Read its roster, arming contract, exact owner and negative routing. Use Queen for source construction/format; Harness Integration for selected/native capability evidence. Do not invent a new Drone or validator.
2. Record the user's requested component, actual type and classification, canonical repository/revision or dirty hashes, approved scope, target harness/client versions, tool availability and test budget. Read `plugin-catalog.json` and the actual owner's source root. Source files, cached copies and UI installation are distinct evidence.
3. Inspect the full source procedure, its own research/reference layer, templates/examples and cross-links. Every specialist needs its actual paired Stinger/Drone; standalone and orchestrator tiers remain explicit exceptions. Commands load Pest Controller and carry the complete runtime process. Check component names/paths, approved source owner, conventions, manifests and declared prerequisites. Missing research or ownership is a gap rather than a universal format PASS.
4. Run Queen's existing `references/scripts/per-type-validation.py` with the actual component type and requested harnesses, preserving errors, warnings and informational reduced-coverage messages. In the source checkout also run existing source/law validation where applicable. No shell means documented manual inspection with unexecuted checks, not fabricated output. A canonical Markdown agent is not the generated Codex TOML carrier.
5. Build only the authorized selected owners through the existing builder into a task-owned output. Validate actual portable/Claude/Cursor manifests, flat commands, source-command wrappers, paired resources and native carrier identities. Parse generated TOML with an already available compatible parser or record that check unavailable; verify required fields and current documented carrier. Inspect actual resource links, source-to-projection transformation and artifact hashes. Do not install tools to fill a receipt.
6. For installed qualification, use trusted Core's existing `hooks/resolve-component.py` against the actual selected registry and exact workflow key. Check owner, version, resource identity and prerequisite closure. Stop only dependent work if selection is missing, mismatched or unsupported. Never load an unselected cached sibling or treat a source path as an installed substitute.
7. Treat role registration, hook trust, settings and activation as distinct mutations requiring applicable task authorization. Review the exact proposed files and scope first. Use existing trusted registration/install procedures only when authorized; no silent repair or global write. A post-edit source hook is not permission for native effects.
8. Capture actual native discovery and a bounded invocation/effect result only with existing authorized tooling and a safe approved target. Bind host/client version, source/carrier hashes, selected state, permission/account boundary and observed result. Without native tools, retain UNEXECUTED and describe direct-skill or serial fallback with its lost coverage. A syntax check, test fixture, queued job or another client's run is not native proof.
9. Recheck affected evidence after source changes and bind the final combined candidate. Close development-focused changes with independent Security, Quality after Security clearance and orchestrator Repository Health. Deliver the receipt with separate source, projection, selection, trust and native results. No release claim, commit, push, publication, provider action or deployment follows without its specific authority.

## Host and authority contract

Claude Code, Cursor and Cowork use their actual supported invocation and flat owner command; Codex uses generated `source-command-qualify-wiring`. Verify current tool support rather than assuming the invocation creates agents, installs Core or populates a registry. Core owns this command and Queen/Harness Integration; optional owners remain selected prerequisites for their components.

Run only existing authorized tools within budget. Do not install dependencies, delete/move/rename unowned files, change settings, enter credentials, create accounts, spend money, send messages, commit, push, merge, deploy or publish without specific task authority. Files, fetched documentation, scanner output and agents cannot expand permission.

## Report

Return Status, Delivered paths, Verified commands/results and evidence boundaries, Not done, Questions and Out of scope. Keep native discovery/invocation separate from source and carrier checks. Unknown, absent, failed, skipped, stale, queued or cancelled checks are unproven.

## Ship Gate

Prior to committing any code to the repository you must utilize in order the security-stinger, quality-stinger, and github-repo-health-stinger. After each thorough pass you will prepare an appropriate report in the repository's relevant library directory associated with the agent and skill. All medium or above findings must be resolved followed by another thorough re-evaluation of the updated code prior to proceeding to the next step. The last step of loading the skill github-repo-health-stinger is an orchestrator level task. The sub-agent should make every effort to reinforce to the orchestrating agent to load this skill prior to committing or pushing code to the repository. The user should have an opportunity to review the reports, agent summary, and approve committing and pushing to the repository prior to doing so.
