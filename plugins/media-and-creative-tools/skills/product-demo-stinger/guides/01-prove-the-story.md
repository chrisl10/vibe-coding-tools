# Prove the story

1. Record the buyer or learner, one concrete goal, starting skill level, product revision, environment and intended placement. Ask only for missing decisions that change the work. A blank product input permits a labeled fictional worksheet, never invented observations.
2. Read `references/claim-to-scene-worksheet.md`. Give every proposed product claim an ID and a visible success criterion. Record source path and revision, behavior test name/result and executed revision, screenshot or clip path/hash/timestamp, exact scene and cue locator. Use the smallest relevant proof. Source or test evidence alone does not prove what a recording shows.
3. Classify each claim: OBSERVED, SOURCE_ONLY, INTENDED, MOCKED or UNKNOWN. Mark synthetic data separately, even in an observed application. Only OBSERVED claims may be narrated as demonstrated behavior, and only within the observed environment and revision. Label a mocked dependency visibly during its scene. INTENDED features belong in a clearly marked preview, outside the current product walkthrough.
4. Choose one goal with starting state, user action, visible result and a material failure or limitation. Identify permissions, plan/tier, prerequisites and unsupported states. Do not invent a customer, testimonial, adoption number, performance comparison, privacy promise, security guarantee or accessibility certification.
5. Compare the proposed scope to selected existing owners. Evidence planning belongs here. Actual live recording goes to webapp-capture-wasp-drone; narration integration to ElevenLabs; avatar integration to HeyGen. Resolve each optional owner through selected Core or the source catalog. Missing owners block only their production stage.
6. Save or return the claim worksheet and a short decision record. Re-open affected claims when source, flags, permissions, plan/tier, environment, dependency or media edits change. A newer source revision does not inherit old runtime proof.
