# Explain security responsibilities before building

Use this when a new builder asks what security work they still own while AI helps. It adds a learning explanation to readiness intake. It does not assess or change their app. Grounding: digest.

1. Start with the user's real milestone and data. Ask only what changes the advice: who uses it, what information it holds, who may read or change it, who can approve work and who handles a reported problem. Unknown people or permissions stay questions.
2. Explain security in plain words: protect private information, prevent unwanted changes and keep the service usable. Sign-in asks who you are. Authorization asks what you may do. Logging in does not give someone permission to see another customer's files. See authorization source.
3. Fill the [responsibility worksheet](../references/templates/security-responsibility-worksheet.md). The product owner sets scope, data needs and budget, and approves consequential actions. AI may explain or propose work within that scope. An authorized implementation owner builds the control. Security reviews actual risk and evidence. Quality checks expected behavior after Security. The named operator owns the response and recovery procedure. No AI draft or diagram transfers that responsibility.
4. Explain the [six boundaries](../references/beginner-security-responsibilities.md). Ask for the selected Auth, DB, Dependency Audit and relevant platform/provider owners when implementation is needed. Core Security retains audit/design ownership. Use trusted Core selection, not guessed roles or a cached sibling path. Missing owners are handoff gaps; do not create a duplicate coach.
5. Use one bounded analogy: a shared workshop has a visitor list and locked drawers. The list identifies visitors; drawer permissions say which tools each may use. The owner decides the rules, a builder fits the locks and a reviewer checks them. Software also has background jobs, copies and remote services, so checking one screen does not prove every path. Keep the real software explanation alongside it.
6. Propose one first-slice evidence question appropriate to the supplied goal. For a private file feature: an allowed user can read their own test file; an unrelated user cannot read it through the actual read route. The implementation/review owners choose and run the target-specific tests only with accepted scope. No credentials, live user records or attack traffic are needed for this learning explanation.
7. Ask one teach-back question: "If AI drafts a private file feature, who decides who may open it, who builds that check, and what evidence would you ask for before real users rely on it?" Record understanding pending until an actual reply supports a narrower observation. An accurate reply does not certify developer competence or app safety.
8. Return one readiness recommendation, filled or explicitly unknown roles, unresolved boundaries, next selected-owner handoff and understanding status. Keep settings, spending, live incidents, deployment and code changes under their existing action authority.

For a report of a live leak or failure, stop the generic lesson and return a concrete handoff to the actual authorized operator and Security owner. Do not probe the app, promise containment or invent a responder. Current owner procedure separates source review, synthetic exercises and actual target evidence.
