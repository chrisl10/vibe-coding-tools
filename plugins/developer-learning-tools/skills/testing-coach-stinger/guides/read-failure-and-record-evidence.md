# Read failure and record evidence

Start with the named assertion, expected value, observed value, candidate identity, command, runtime and exit result. A failure means this observation did not meet this assertion under this setup. It does not prove the exact root cause; setup errors, a wrong expectation or the implementation can explain it. Expected rejection assertions pass when the required exception occurs; an uncaught exception is an error, not automatically useful bug detection. See unittest reporting and pytest exception assertions.

A green run supports only executed assertions on the actual candidate. Test count and line coverage do not independently establish behavior, security, concurrency, integration or production readiness. Keep skipped, unrun, expected deliberate failures and unexpected failures distinct. Do not weaken an assertion just to make a faulty candidate green. Route product test design to the selected runtime owner and final plan verification to Core Quality after Security.

Record the learner's actual prediction, attempt, support used, retry, changed-condition response and teach-back separately from tool execution. Without an observed learner response, understanding is PENDING. A copied passing solution is not independent practice. Chat is default; persistent records or exercise writes need current explicit scope authorization through the orchestrator. Keep personal learner data and private app code out of uploads.
